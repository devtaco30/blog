안녕하세요. 이 시리즈는 F-lab 멘토링 프로젝트로 주식 거래 엔진을 직접 설계하고 구현한 과정을 기록한 글입니다.

백엔드 개발자로 일하다 보면 어느 순간 이런 생각이 듭니다.

"나는 지금 기술을 쓰고 있는 건가, 아니면 그냥 프레임워크를 조립하고 있는 건가?"

Spring Boot로 CRUD를 만들고, JPA로 쿼리를 날리고, Kafka를 설정파일 몇 줄로 붙이는 건 할 수 있습니다. 그런데 왜 그렇게 하는지, 어떤 트레이드오프가 있는지, 다르게 하면 어떻게 되는지를 설명할 수 있는가?

이 시리즈는 그 질문에 답하기 위해 시작한 프로젝트의 기록입니다. 매 설계 결정마다 왜 그 선택을 했는지, 어떤 트레이드오프가 있는지를 기록하는 것이 목표입니다.

🎯 1. 왜 주식 거래 엔진인가

프로젝트 선택 기준

F-lab 멘토링을 진행하면서 학습용 프로젝트를 선택해야 했습니다. 기준은 세 가지였습니다.

기준은 세 가지였습니다.

  • 동시성이 중요할 것: 여러 사용자가 동시에 접근하고, 데이터 정합성이 깨지면 안 되는 도메인
  • 설계 결정이 성능에 직접 영향을 줄 것: 자료구조 하나, 아키텍처 하나가 처리량을 수십 배 바꾸는 환경
  • 점진적으로 복잡도를 올릴 수 있을 것: 단순한 구조에서 시작해 MSA까지 자연스럽게 진화 가능한 구조

주식 거래 엔진은 이 세 가지를 모두 만족했습니다.

주식 거래 엔진이 적합한 이유:

  • 매수·매도 주문이 동시에 쏟아지고, 잔고와 보유 수량은 정합성이 깨지면 안 됩니다
  • 오더북 자료구조 선택이 매칭 속도를 결정합니다
  • 단일 JAR에서 시작해 마이크로서비스까지 자연스럽게 진화할 수 있습니다

🏗️ 2. 프로젝트 구조 개요

멀티모듈 구성

멀티모듈 Spring Boot 프로젝트로 구성했습니다. 각 모듈이 자기 도메인을 책임지고, api 모듈이 이를 조합합니다.

stock-trading-engine
├── core        — Snowflake ID, 공유 DTO, 예외 계층
├── user        — 사용자, Redis 불투명 토큰 인증
├── market      — 종목·시세 마스터 데이터
├── account     — 계좌·잔고·보유 종목
├── trading     — 주문 접수·취소, 인메모리 오더북
├── settlement  — T+2 정산
└── api         — 컨트롤러, API 서비스 (orchestration)

의존 방향은 단방향입니다.

core → user / market / account / trading / settlement → api

상위 모듈(api)이 하위 모듈에 의존합니다. 역방향 의존은 허용하지 않습니다. Phase 3에서 서비스를 분리할 때 이 경계가 마이크로서비스 경계가 됩니다.

Phase 로드맵

이 프로젝트는 처음부터 복잡하게 시작하지 않았습니다. 단계적으로 복잡도를 올렸습니다.

Phase구조핵심 변경
Phase 1단일 JAR, 모든 모듈 같은 JVM도메인 모델 검증
Phase 2물리적 프로세스 분리 (api / matching / settlement)Kafka 기반 비동기 파이프라인
Phase 3MSA — 서비스별 DB 분리Saga 패턴, CQRS

비유:

  • Phase 1은 "일단 동작하는 MVP"입니다
  • Phase 2는 "병목을 제거하고 독립 배포를 가능하게 하는 구조"입니다
  • Phase 3는 "서비스별 완전한 자율성"입니다

📌 3. 이 시리즈에서 다루는 핵심 질문들

오더북 설계 (Part 3)

오더북(Order Book)은 거래소의 심장입니다. 매수·매도 주문이 실시간으로 쌓이고, 체결 가능한 쌍을 찾아 매칭합니다.

처음 마주한 질문은 단순했습니다.

"호가창은 어떻게 유지되는가?"

주문이 들어오면 호가창에 추가되고, 체결되면 수량이 줄고, 취소되면 사라집니다. 이 상태를 소프트웨어로 어떻게 표현할 것인가? 수많은 주문이 가격과 시간 순서를 유지하면서 정합성 있게 관리되려면 어떤 구조가 필요한가?

이 질문을 따라가다 보면 자연스럽게 "어떤 연산이 자주 일어나는가"가 보이기 시작합니다. 그제서야 자료구조 선택의 문제가 됩니다.

동시성 (Part 4)

오더북을 완성하고 나면 다음 문제가 기다리고 있습니다.

"동일 종목 주문이 동시다발적으로 들어오면 어떻게 될까?"

TreeMap과 ArrayDeque는 스레드 안전하지 않습니다. 두 스레드가 동시에 접근하면 내부 구조가 깨집니다. 그러면 동기화가 필요합니다. synchronized를 쓰면 해결은 되는데, 성능 문제가 생깁니다. 락 경합이 발생하고, 서버를 여러 대로 늘리면 이 구조 자체가 성립하지 않습니다.

단일 서버에서의 동기화 문제와, 스케일 아웃 시 오더북 일관성 문제를 어떻게 풀 것인가.

아키텍처 진화 (Part 5, 6)

Phase 1을 완성하고 나면 구조적인 한계가 보입니다.

"매칭 엔진을 붙이면 API 스레드가 매칭까지 담당하게 된다. 이게 맞는 구조인가?"

처리량을 높이려면 매칭을 별도 프로세스로 분리해야 합니다. 어떻게 분리할 것인가, 분리하면 어떤 새로운 문제가 생기는가. 실제 금융기관은 이 문제를 어떻게 풀었는가.

🔗 4. 설계 결정 기록 (ADR)

이 시리즈의 모든 설계 결정은 ADR(Architecture Decision Record)로 기록했습니다.

ADR(Architecture Decision Record)은 설계 결정을 내릴 때 "왜 그 선택을 했는지", "어떤 대안을 검토했는지", "어떤 트레이드오프가 있는지"를 문서로 남기는 방식입니다. 코드만 보면 결과만 보이지만, ADR을 보면 그 결정에 이르는 과정이 보입니다.

ADR결정 내용
ADR-001예약증거금 합산을 DB SUM 쿼리로 교체 — 비관적 락 보유 시간 단축
ADR-003Account → Holding 순서로만 락 획득 — 데드락 방지
ADR-004Stateless API + accountId 파티셔닝 — 비관적 락 경합 구조적 제거
ADR-005Order.accountId 직접 보유 — LazyInitializationException 구조적 방지
ADR-006TreeMap + ArrayDeque + Lazy Removal — 오더북 자료구조 선택

설계 결정에는 항상 트레이드오프가 있습니다. "왜 그걸 골랐는가"를 설명할 수 있는 것이 기술의 깊이입니다.
