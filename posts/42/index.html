[6년차 쯤 되면 좀 알자] 그럼 GC 는 뭔데? - 2부 -

G1GC가 Young GC, Mixed GC, Full GC를 각각 어떤 단계로 수행하는지 따라갑니다. | 예제 코드로 객체 할당과 RSet 업데이트를 확인하고, 튜닝 목표와 모니터링 포인트로 끝납니다.

안녕하세요. Java/Kotlin 백엔드 개발자로서 G1GC(Garbage-First Garbage Collector)를 완벽하게 이해하는 것은 대규모 애플리케이션의 성능 최적화에 필수적입니다.

본 포스팅(2부)에서는 G1GC의 실제 동작 과정을 단계별로 아주 자세하게 분석하고, 실제 코드 예제와 실무 활용 방법을 다룹니다.

1부에서는 기본 개념과 핵심 원리(Region, RSet, CSet, SATB, TAMS, Tri-Color Marking, STW)를 다뤘습니다.

🔄 1. G1GC가 실제로 어떻게 동작하나요?

1-1. Young GC (Minor GC) - 단계별 상세 설명

Young GC는 Eden Region이 가득 찰 때 발생합니다.

Step 1: Initial Mark (STW) - 시작 마킹

"누가 살아있는지 시작점을 찾는 단계"

1. Root Set 확인
   - Stack의 지역 변수들
   - Static 변수들
   - JNI 참조들
   
2. Root Set에서 직접 참조되는 객체 마킹
   - Gray로 표시
   
3. TAMS 설정
   - 각 Region의 현재 할당 위치 기록
   - 이후 할당된 객체는 자동으로 살아있음

예시:

public static void main(String[] args) {
    A a = new A();  // Stack에 a 변수
    B b = new B();  // Stack에 b 변수
}

// Initial Mark:
// Root Set: Stack의 a, b
// → A 객체, B 객체를 Gray로 마킹

메모리 상태:

┌─────────────────────────────────────┐
│  Root Set                           │
├─────────────────────────────────────┤
│  Stack: a → A 객체 (Gray)           │
│  Stack: b → B 객체 (Gray)           │
│  Method Area: A.STR → "ABC" (Gray)  │
└─────────────────────────────────────┘

Step 2: Concurrent Marking - 동시 마킹

"애플리케이션과 동시에 마킹하는 단계"

⚠️ 이 단계는 STW가 아닙니다! 애플리케이션이 계속 실행됩니다.

반복:
  1. Gray 객체 하나 선택
  2. 자식 객체 확인
     - White → Gray로 변경
  3. 현재 객체 → Black
  
Write Barrier:
  - 참조 변경 감지
  - White 객체 → Gray로 변경
  - SATB Queue에 기록

동시 실행:

애플리케이션:          GC:
  객체 사용            Gray 객체 처리
  새 객체 생성         객체 그래프 탐색
  참조 변경           Write Barrier 처리

예시:

// Marking 시작: A 객체 (Gray)
A a = new A();
B b = new B();
a.ref = b;

// Concurrent Marking:
// 1. A 객체 확인 (Gray → Black)
// 2. A의 자식 확인: a.ref = b
// 3. B 객체 발견 (White → Gray)
// 4. B 객체 확인 (Gray → Black)

// 동시에 애플리케이션 실행:
C c = new C();  // 새 객체 생성 (TAMS 이후, 자동 살아있음)
a.ref = c;      // 참조 변경 (Write Barrier 처리)

Step 3: Remark (STW) - 재확인

"동시 마킹 중 변경사항을 최종 확인하는 단계"

1. SATB Queue 처리
   - Marking 시작 시점의 참조 마킹
   
2. 모든 Gray 객체 처리
   - 남은 Gray → Black
   
3. Weak Reference 처리
   - 약한 참조 객체 정리

왜 필요한가요?

  • 동시 Marking 중 참조가 변경됨
  • 변경사항을 최종 확인해야 함
  • 일관성 보장

Step 4: Cleanup - 정리

"수집할 Region을 결정하는 단계"

1. 각 Region의 가비지 비율 계산
2. CSet 선택
   - 가비지가 많은 Region 우선
3. Freelist 업데이트
   - 빈 Region 추가

예시:

Region 0: 가비지 80% → CSet 포함
Region 1: 가비지 20% → CSet 제외
Region 2: 가비지 90% → CSet 포함 (우선순위 높음)

Step 5: Evacuation (STW) - 이동

"살아있는 객체를 다른 Region으로 복사하는 단계"

⚠️ 이 단계가 가장 중요한 STW입니다!

CSet의 각 Region에 대해:
  1. 살아있는 객체 식별 (Black 객체)
  2. 대상 Region 선택 (Survivor 또는 Old)
  3. 객체 복사
  4. 참조 업데이트
  5. 원본 Region 해제

예시:

Region A (Eden, CSet):
  A 객체 (Black) → Region B (Survivor)로 복사
  C 객체 (White) → 수집 (가비지)
  
참조 업데이트:
  Stack의 a → Region B의 A 객체 (새 주소)
  RSet 업데이트

비유:

  • 이사: 살아있는 물건만 새 집으로 옮기기
  • 옮긴 후 주소 변경 (참조 업데이트)
  • 옛 집 정리 (원본 Region 해제)

1-2. Mixed GC

Mixed GC는 Old Generation도 함께 수집합니다.

Young GC vs Mixed GC:

Young GC:
  - Eden + Survivor Region만 수집
  
Mixed GC:
  - Eden + Survivor + 일부 Old Region 수집
  - Old Region은 가비지 비율이 높은 것부터

언제 발생하나요?

  1. IHOP 도달: Old Generation이 일정 비율 도달
  2. 가비지 비율: Old Region의 가비지 비율이 높을 때

1-3. Full GC (피해야 함!)

Full GC는 G1GC의 최후의 수단입니다.

발생 조건:

  1. Evacuation 실패: 살아있는 객체를 복사할 공간이 없을 때
  2. 메모리 부족: Freelist에 빈 Region이 없을 때
  3. 명시적 호출: System.gc() 호출 시

특징:

  • 전체 힙 수집
  • 긴 STW 시간 (예측 불가능)
  • 회피해야 함!

📊 2. 실제 코드로 이해하기

예제 코드

class A {
    private static final String STR = "ABC";
    private static Long l = Long.valueOf(-1L);
    private static int i = -1;
    private static C c = new C();

    private final String a = "ABC";
    private final int ii = 1;
    private C cc = new C();

    public static void main(String[] args) {
        A a = new A();
        B b = new B();
        System.out.println(A.STR);

        System.out.println(A.STR == a.a); // true? false?
        System.out.println(A.STR == "ABC"); // true? false?

        System.out.println(A.l == new Long(-1L)); // true? false?
        System.out.println(A.l == Long.valueOf(-1L)); // true? false?
    }
}

객체 할당 과정

main 메서드 실행:
  1. A a = new A();
     - Freelist에서 Region 가져옴
     - Region을 Eden으로 설정
     - A 객체 할당
     
  2. B b = new B();
     - 또 다른 Region에서 B 객체 할당
     
  3. String 비교
     - "ABC"는 String Constant Pool에 있음
     - 참조만 확인 (객체 생성 없음)

Young GC 발생 시

Eden Region 가득 참:
  
  1. Initial Mark (STW)
     - Root Set: Stack의 a, b
     - A 객체, B 객체 마킹
     
  2. Concurrent Marking
     - A 객체의 필드 확인
     - B 객체의 필드 확인
     - 참조된 객체들 마킹
     
  3. Remark (STW)
     - 최종 확인
     
  4. Evacuation (STW)
     - 살아있는 객체 → Survivor Region
     - 가비지 수집

RSet 업데이트 예시

A 객체가 C 객체 참조:
  A 객체 (Old Region)
    → C 객체 (Eden Region)
    
C 객체의 Region RSet 업데이트:
  - A 객체의 Region 정보 기록
  - Write Barrier가 자동 처리

🎓 핵심 정리

1. ⚠️ Region 기반 구조

  • 힙을 작은 Region으로 나눔
  • Region 단위로 빠르게 수집
  • 예측 가능한 성능

2. ⚠️ RSet은 필수!

  • 다른 Region 간 참조 추적
  • Region 단위 GC의 핵심
  • Write Barrier로 자동 업데이트

3. ⚠️ STW는 필수지만 최소화

  • 객체 그래프 일관성 보장
  • G1GC는 STW를 최소화하지만 완전히 제거할 수는 없음
  • 예측 가능한 짧은 STW 시간

4. ⚠️ Tri-Color Marking

  • White, Gray, Black으로 상태 구분
  • 동시 Marking 시 Write Barrier 필요
  • SATB로 일관성 보장

5. ⚠️ SATB와 TAMS

  • SATB: Marking 시작 시점 스냅샷
  • TAMS: 새 객체 자동 마킹
  • 동시 Marking의 핵심 기법

💡 실무에서 기억할 것

G1GC 튜닝 목표

  1. STW 시간 최소화: -XX:MaxGCPauseMillis=200
  2. Full GC 회피: 충분한 메모리 할당
  3. 처리량 최적화: Region 크기 조정

모니터링 포인트

  1. GC 로그 분석: STW 시간, GC 빈도 확인
  2. RSet 크기: RSet이 너무 크면 성능 저하
  3. Evacuation 실패: Full GC 위험 신호

이상으로 G1GC의 실제 동작 과정과 실무 활용 방법을 설명했습니다. 1부와 2부를 통해 G1GC의 내부 동작 원리를 완벽하게 이해하실 수 있을 것입니다.
