안녕하세요. Java/Kotlin 백엔드 개발자로서 운영체제 스레드를 이해하는 것은 멀티스레딩 프로그래밍과 성능 최적화에 필수적입니다.

본 포스팅(1부)에서는 운영체제 관점에서 프로세스와 스레드의 차이, 스레드의 메모리 구조, 스레드 스케줄링, 컨텍스트 스위칭 등 핵심 개념들을 심층적으로 설명합니다.

2부에서는 Java Thread 객체와 운영체제 스레드의 관계, JVM의 스레드 관리 방식, 실제 동작 과정을 다룹니다.

🎯 1. 프로세스와 스레드의 관계

⚠️ 핵심: 프로세스는 컨테이너, 스레드는 실행 단위

프로세스와 스레드는 비교 대상이 아닙니다!

정확한 관계:

  • 프로세스: 메모리 공간을 가진 컨테이너
  • 스레드: 프로세스 내에서 실제 작업을 수행하는 실행 단위
  • 관계: 프로세스 안에 스레드가 존재 (포함 관계)

비유:

  • 프로세스: 공장 건물 (메모리 공간 = 작업 공간)
  • 스레드: 공장 안에서 일하는 작업자들 (실제 작업 수행)
  • 공장(프로세스) 안에 작업자(스레드)들이 있어야 공장이 돌아감

프로세스(Process)란?

프로세스는 "하나의 프로그램이 실행되는 독립적인 메모리 공간"입니다.

⚠️ 핵심:

  • 하나의 프로그램 = 하나의 프로세스 (일반적으로)
  • 독립적인 메모리 공간 (다른 프로세스와 완전히 격리)
  • 프로세스 간 서로 접근 불가 (메모리 보호)

특징:

  • 독립적인 메모리 공간을 가짐 (Code, Data, Heap)
  • 각 프로세스는 고유한 PID(Process ID)를 가짐
  • 프로세스 안에 하나 이상의 스레드가 존재
  • 프로세스 자체는 실행하지 않음 (스레드가 실행함)
  • 다른 프로세스의 메모리에 직접 접근 불가 (보안)

예시:

크롬 브라우저 실행:
  → 크롬 프로세스 생성 (PID: 1234)
  → 크롬 프로그램이 이 프로세스 안에서 실행됨
  → 이 프로세스는 독립적인 메모리 공간을 가짐

메모장 실행:
  → 메모장 프로세스 생성 (PID: 5678)
  → 메모장 프로그램이 이 프로세스 안에서 실행됨
  → 크롬 프로세스와 완전히 독립적 (서로 접근 불가)

⚠️ 참고: 같은 프로그램도 여러 프로세스로 실행 가능

크롬 브라우저 창 3개 열기:
  → 프로세스 1 (PID: 1234) - 창 1
  → 프로세스 2 (PID: 5678) - 창 2
  → 프로세스 3 (PID: 9012) - 창 3
  
  → 같은 프로그램이지만 각각 독립적인 프로세스
  → 각 프로세스는 완전히 독립적인 메모리 공간

메모리 구조:

프로세스 A (컨테이너):
┌─────────────────────┐
│  Code (코드)         │ ← 공유 메모리
│  Data (데이터)       │ ← 공유 메모리
│  Heap (힙)          │ ← 공유 메모리
├─────────────────────┤
│  Stack (스레드1)    │ ← 스레드1의 작업 공간
│  Stack (스레드2)    │ ← 스레드2의 작업 공간
└─────────────────────┘

프로세스 B (컨테이너):
┌─────────────────────┐
│  Code (코드)         │
│  Data (데이터)       │
│  Heap (힙)          │
├─────────────────────┤
│  Stack (스레드1)    │
└─────────────────────┘

→ 프로세스 A와 B는 완전히 독립적인 메모리 공간
→ 각 프로세스 안에 스레드들이 존재

스레드(Thread)란?

스레드는 "프로세스 내에서 실제 작업을 수행하는 실행 단위"입니다.

⚠️ 핵심: 프로세스가 돌아가게 하는 것은 스레드입니다!

⚠️ 참고: OS 스레드 = 커널 스레드

일반적으로 "OS 스레드"라고 하면 "커널이 관리하는 스레드"를 의미합니다:

  • OS 스레드 = 커널 스레드 (같은 의미)
  • OS가 관리하는 스레드 = 커널이 관리하는 스레드
  • 커널 모드에서 스케줄링되고 관리됨

특징:

  • 프로세스 안에 존재 (프로세스 없이 스레드 존재 불가)
  • 같은 프로세스 내의 스레드들은 Code, Data, Heap을 공유
  • 각 스레드는 독립적인 스택 메모리를 가짐 (작업 공간)
  • 스레드가 실제로 CPU에서 코드를 실행함
  • OS(커널)가 스레드를 스케줄링하고 관리함

메모리 구조:

프로세스 (컨테이너):
┌─────────────────────┐
│  Code (공유)         │ ← 모든 스레드가 공유하는 코드
│  Data (공유)         │ ← 모든 스레드가 공유하는 데이터
│  Heap (공유)        │ ← 모든 스레드가 공유하는 힙
├─────────────────────┤
│  Stack (스레드1)    │ ← 스레드1의 작업 공간
│  Stack (스레드2)    │ ← 스레드2의 작업 공간
│  Stack (스레드3)    │ ← 스레드3의 작업 공간
└─────────────────────┘

→ 프로세스는 메모리 컨테이너
→ 스레드들이 실제로 작업을 수행
→ 스레드가 없으면 프로세스는 아무것도 하지 않음

프로세스와 스레드의 차이점 (참고용)

구분프로세스스레드
메모리독립적인 메모리 공간공유 메모리 (Code, Data, Heap)
통신IPC 필요 (파이프, 소켓 등)공유 메모리로 직접 통신
생성 비용높음 (메모리 복사 등)낮음 (스택만 생성)
독립성완전히 독립적같은 프로세스 내에서 공유
안정성한 프로세스가 죽어도 다른 프로세스에 영향 없음한 스레드가 죽으면 전체 프로세스에 영향
컨텍스트 스위칭느림 (메모리 공간 전환)빠름 (스택만 전환)

비유 (수정):

  • 프로세스: 공장 건물 (메모리 공간 = 작업 공간)
  • 스레드: 공장 안에서 일하는 작업자들 (실제 작업 수행)
  • 공장(프로세스) 안에 작업자(스레드)들이 있어야 공장이 돌아감
  • 작업자(스레드) 없이는 공장(프로세스)이 아무것도 할 수 없음

🏗️ 2. 스레드의 메모리 구조

스레드별 독립적인 스택

⚠️ 핵심: 각 스레드는 독립적인 스택 메모리를 가집니다. (공유되지 않음!)

스택의 용도:

  • 메서드 호출 정보 (스택 프레임)
  • 지역 변수
  • 매개변수
  • 반환 주소

⚠️ 중요한 점:

  • 스택은 공유되지 않습니다!
  • 각 스레드는 자신만의 스택을 가짐
  • 스레드1의 스택과 스레드2의 스택은 완전히 독립적

예시:

public void methodA() {
    int a = 10;  // 스레드1의 스택에 저장
    methodB(a);
}

public void methodB(int param) {
    int b = 20;  // 스레드1의 스택에 저장
}

메모리 구조:

스레드1의 스택:
┌─────────────────────┐
│  methodB 스택 프레임  │
│  - param: 10        │
│  - b: 20            │
├─────────────────────┤
│  methodA 스택 프레임  │
│  - a: 10            │
└─────────────────────┘

스레드2의 스택:
┌─────────────────────┐
│  methodA 스택 프레임  │
│  - a: 30            │ ← 스레드1과 독립적
└─────────────────────┘

공유 메모리 영역

같은 프로세스 내의 모든 스레드가 공유하는 메모리:

  1. Code 영역 (코드)

    • 프로그램의 실행 코드
    • 읽기 전용 (Read-Only)
    • 모든 스레드가 같은 코드를 실행

  2. Data 영역 (데이터)

    • 전역 변수
    • Static 변수
    • 모든 스레드가 접근 가능

  3. Heap 영역 (힙)

    • 동적으로 할당된 메모리
    • 객체들이 저장되는 곳
    • 모든 스레드가 접근 가능

예시:

class SharedData {
    private static int count = 0;  // Data 영역 (공유)
    
    public void increment() {
        count++;  // 모든 스레드가 같은 count를 공유
    }
}

메모리 구조:

프로세스 메모리:
┌─────────────────────┐
│  Code (공유)         │ ← 모든 스레드가 공유
│  Data (공유)         │ ← 모든 스레드가 공유
│  Heap (공유)        │ ← 모든 스레드가 공유
├─────────────────────┤
│  Stack (스레드1)    │ ← 스레드1만 사용 (공유 안됨!)
│  Stack (스레드2)    │ ← 스레드2만 사용 (공유 안됨!)
└─────────────────────┘

⚠️ 핵심:
- Code, Data, Heap: 공유됨 ✅
- Stack: 공유 안됨 ❌ (각 스레드가 독립적으로 가짐)

⚠️ 스레드 간 통신: 공유 메모리로 직접 통신

핵심: 스레드는 같은 Heap 영역을 공유하므로, 객체를 통해 직접 통신합니다!

프로세스 간 통신 vs 스레드 간 통신:

프로세스 간 통신 (IPC):

프로세스 A:                    프로세스 B:
┌─────────────┐              ┌─────────────┐
│  Heap A     │              │  Heap B     │
│  (독립적)    │              │  (독립적)    │
└─────────────┘              └─────────────┘
      ↓                            ↑
      └──── 파이프/소켓 ────────────┘
      (OS를 통한 통신 필요)

스레드 간 통신 (공유 메모리):

프로세스:
┌─────────────────────┐
│  Heap (공유)        │ ← 모든 스레드가 같은 Heap 사용
│  ┌───────────────┐ │
│  │  객체 A       │ │ ← 스레드1이 생성
│  └───────────────┘ │
│  ┌───────────────┐ │
│  │  객체 B       │ │ ← 스레드2가 생성
│  └───────────────┘ │
├─────────────────────┤
│  Stack (스레드1)    │ → Heap의 객체 A 참조
│  Stack (스레드2)    │ → Heap의 객체 B 참조
└─────────────────────┘

→ 같은 Heap을 공유하므로 직접 참조 가능
→ OS를 통한 통신 불필요!

실제 예시:

class SharedObject {
    private String message = "";
    
    public void setMessage(String msg) {
        this.message = msg;  // Heap에 저장
    }
    
    public String getMessage() {
        return this.message;  // Heap에서 읽기
    }
}

// 메인 스레드
SharedObject shared = new SharedObject();  // Heap에 객체 생성

// 스레드1
Thread thread1 = new Thread(() -> {
    shared.setMessage("Hello from Thread1");  // Heap의 객체 수정
});

// 스레드2
Thread thread2 = new Thread(() -> {
    String msg = shared.getMessage();  // Heap의 객체 읽기
    System.out.println(msg);  // "Hello from Thread1" 출력
});

메모리 구조:

프로세스 Heap (공유):
┌─────────────────────┐
│  SharedObject       │ ← 스레드1과 스레드2가 모두 참조
│  - message: "..."   │
└─────────────────────┘
         ↑              ↑
         │              │
스레드1 Stack      스레드2 Stack
(shared 참조)      (shared 참조)

→ 같은 Heap의 같은 객체를 참조
→ 스레드1이 수정하면 스레드2가 바로 읽을 수 있음
→ OS를 통한 통신 불필요!

비유:

  • 프로세스 간 통신: 다른 아파트에 사는 사람들 (전화/문자 필요)
  • 스레드 간 통신: 같은 아파트 안의 사람들 (같은 거실에서 직접 대화)

핵심 정리:

  • 스레드는 같은 Heap을 공유
  • 스레드1이 Heap에 객체를 만들면, 스레드2가 그 객체를 참조 가능
  • 이게 "공유 메모리로 직접 통신"하는 것
  • OS를 통한 통신(파이프, 소켓) 불필요!

⚠️ OS 레벨의 메모리 관리: 가상 메모리와 페이지

⚠️ 핵심: 프로세스가 보는 메모리 주소는 "가상 주소"이며, OS가 이를 "물리 주소"로 변환합니다!

가상 메모리 (Virtual Memory)란?

정의:

  • 가상 메모리: 프로세스가 보는 메모리 주소 공간 (논리적 주소)
  • 물리 메모리: 실제 RAM의 메모리 주소 공간 (물리적 주소)
  • 변환: OS가 가상 주소를 물리 주소로 변환

왜 필요한가요?

  1. 메모리 보호

    • 각 프로세스가 독립적인 가상 주소 공간을 가짐
    • 프로세스 A가 프로세스 B의 메모리에 접근 불가
    • 보안과 안정성 보장

  2. 메모리 확장

    • 가상 메모리 크기 > 물리 메모리 크기 가능
    • 디스크(스왑)를 사용하여 메모리 확장
    • 더 많은 프로세스 실행 가능

  3. 단순화

    • 각 프로세스가 0부터 시작하는 주소 공간을 가짐
    • 메모리 관리 단순화

예시:

프로세스 A의 가상 주소 공간:
0x00000000 ~ 0xFFFFFFFF (4GB 가상 메모리)

프로세스 B의 가상 주소 공간:
0x00000000 ~ 0xFFFFFFFF (4GB 가상 메모리)

→ 둘 다 같은 가상 주소를 사용하지만, 실제 물리 메모리는 다름!
→ OS가 각 프로세스의 가상 주소를 다른 물리 주소로 매핑

페이지 (Page)와 페이지 프레임 (Page Frame)

⚠️ 핵심: OS는 메모리를 고정 크기의 "페이지" 단위로 관리합니다!

정의:

  • 페이지 (Page): 가상 메모리를 나눈 고정 크기 단위
  • 페이지 프레임 (Page Frame): 물리 메모리를 나눈 고정 크기 단위
  • 페이지 사이즈 (Page Size): 일반적으로 4KB (4096 bytes)

페이지 사이즈:

  • 일반적인 크기: 4KB (4096 bytes)
  • 대형 페이지 (Huge Page): 2MB, 1GB 등 (성능 최적화용)
  • 시스템에 따라 다름: Linux는 보통 4KB, 일부 시스템은 8KB

메모리 구조:

가상 메모리 (프로세스가 보는 주소):
┌─────────────┐
│  Page 0     │ (0x0000 ~ 0x0FFF) - 4KB
│  Page 1     │ (0x1000 ~ 0x1FFF) - 4KB
│  Page 2     │ (0x2000 ~ 0x2FFF) - 4KB
│  ...        │
└─────────────┘

물리 메모리 (실제 RAM):
┌─────────────┐
│  Frame 0    │ (실제 물리 주소)
│  Frame 1    │ (실제 물리 주소)
│  Frame 2    │ (실제 물리 주소)
│  ...        │
└─────────────┘

→ OS가 Page를 Frame에 매핑

왜 페이지 단위로 관리하나요?

  1. 효율성

    • 작은 단위로 관리하면 오버헤드 증가
    • 큰 단위로 관리하면 낭비 발생
    • 4KB는 균형잡힌 크기

  2. 단순화

    • 고정 크기로 관리하면 단순함
    • 메모리 할당/해제가 쉬움

  3. 캐시 효율

    • CPU 캐시 라인과 맞춤
    • 성능 최적화

페이지 테이블 (Page Table)

⚠️ 핵심: 페이지 테이블은 가상 주소를 물리 주소로 변환하는 매핑 테이블입니다!

정의:

  • 페이지 테이블: 각 프로세스마다 존재하는 테이블
  • 역할: 가상 페이지 번호 → 물리 프레임 번호 변환
  • 위치: 메모리에 저장 (각 프로세스마다 별도)

구조:

페이지 테이블 (프로세스 A):
┌─────────────┬─────────────┐
│ 가상 페이지  │ 물리 프레임  │
├─────────────┼─────────────┤
│ Page 0      │ Frame 100   │
│ Page 1      │ Frame 200   │
│ Page 2      │ Frame 50    │
│ ...         │ ...         │
└─────────────┴─────────────┘

→ 가상 주소 0x1234 (Page 0 내부) → 물리 주소 Frame 100 + 오프셋

주소 변환 과정:

1. 가상 주소: 0x1234
   ├─ 페이지 번호: 0x1 (Page 1)
   └─ 오프셋: 0x234 (페이지 내부 위치)

2. 페이지 테이블 조회:
   ├─ Page 1 → Frame 200
   └─ 물리 주소 = Frame 200 + 오프셋 0x234

3. 실제 물리 메모리 접근

⚠️ 중요한 점:

  • 각 프로세스마다 별도의 페이지 테이블 존재
  • 프로세스 컨텍스트 스위칭 시 페이지 테이블도 전환
  • 이것이 프로세스 컨텍스트 스위칭 비용이 높은 이유!

MMU (Memory Management Unit)

⚠️ 핵심: MMU는 CPU 내부에 있는 하드웨어로, 가상 주소를 물리 주소로 변환합니다!

정의:

  • MMU (Memory Management Unit): CPU 내부 하드웨어
  • 역할: 가상 주소 → 물리 주소 변환 (페이지 테이블 사용)
  • 위치: CPU 내부 (하드웨어 레벨)

동작 과정:

1. CPU가 가상 주소 접근 요청
   ↓
2. MMU가 페이지 테이블 조회
   ↓
3. MMU가 가상 주소 → 물리 주소 변환
   ↓
4. 실제 물리 메모리 접근

TLB (Translation Lookaside Buffer):

  • 정의: MMU 내부의 캐시
  • 역할: 자주 사용되는 페이지 테이블 항목을 캐시
  • 효과: 페이지 테이블 조회 속도 향상 (캐시 히트 시)

TLB 동작:

1. 가상 주소 접근
   ↓
2. TLB에서 먼저 확인 (캐시)
   ├─ TLB 히트 → 바로 물리 주소 변환 (빠름!)
   └─ TLB 미스 → 페이지 테이블 조회 (느림)
      ↓
      TLB에 캐시 저장

비유:

  • 페이지 테이블: 전화번호부 (전체 목록)
  • TLB: 자주 쓰는 번호를 적어둔 메모 (빠른 접근)

페이지 폴트 (Page Fault)

⚠️ 핵심: 페이지가 물리 메모리에 없을 때 발생하는 예외입니다!

발생 상황:

  1. 페이지가 스왑(디스크)에 있는 경우

    • 물리 메모리가 부족하여 디스크로 스왑됨
    • 페이지 폴트 발생 → 디스크에서 메모리로 로드

  2. 페이지가 아직 할당되지 않은 경우

    • 프로세스가 처음 접근하는 페이지
    • 페이지 폴트 발생 → 물리 메모리 할당

  3. 접근 권한 위반

    • 읽기 전용 페이지에 쓰기 시도
    • 페이지 폴트 발생 → 예외 처리

처리 과정:

1. CPU가 가상 주소 접근
   ↓
2. MMU가 페이지 테이블 조회
   ↓
3. 페이지가 물리 메모리에 없음 (페이지 폴트 발생!)
   ↓
4. OS가 페이지 폴트 처리:
   ├─ 스왑에서 메모리로 로드
   ├─ 물리 메모리 할당
   └─ 페이지 테이블 업데이트
   ↓
5. 원래 명령어 재실행

프로세스와 스레드의 메모리 매핑

⚠️ 핵심: 프로세스는 독립적인 가상 주소 공간을 가지지만, 스레드는 같은 가상 주소 공간을 공유합니다!

프로세스:

프로세스 A:
├─ 가상 주소 공간: 0x00000000 ~ 0xFFFFFFFF
├─ 페이지 테이블 A (독립적)
└─ 물리 메모리 매핑 (독립적)

프로세스 B:
├─ 가상 주소 공간: 0x00000000 ~ 0xFFFFFFFF (같은 가상 주소!)
├─ 페이지 테이블 B (독립적)
└─ 물리 메모리 매핑 (독립적, 프로세스 A와 다름!)

→ 같은 가상 주소를 사용하지만, 다른 물리 메모리 매핑

스레드:

프로세스 (가상 주소 공간):
├─ 가상 주소: 0x00000000 ~ 0xFFFFFFFF
├─ 페이지 테이블 (공유)
└─ 물리 메모리 매핑 (공유)

스레드1:
├─ 같은 가상 주소 공간 사용
├─ 같은 페이지 테이블 사용
└─ 같은 물리 메모리 매핑 사용

스레드2:
├─ 같은 가상 주소 공간 사용
├─ 같은 페이지 테이블 사용
└─ 같은 물리 메모리 매핑 사용

→ 모든 스레드가 같은 가상 주소 공간과 페이지 테이블 공유

컨텍스트 스위칭과 페이지 테이블:

프로세스 컨텍스트 스위칭:

프로세스 A → 프로세스 B:
1. 프로세스 A의 레지스터 저장
2. 페이지 테이블 전환 (A → B) ← 비용 높음!
3. TLB 플러시 (다른 페이지 테이블이므로)
4. 프로세스 B의 레지스터 복원
→ 비용 높음!

스레드 컨텍스트 스위칭:

스레드1 → 스레드2 (같은 프로세스):
1. 스레드1의 레지스터 저장
2. 페이지 테이블 전환 없음! (같은 프로세스)
3. TLB 유지 (같은 페이지 테이블)
4. 스레드2의 레지스터 복원
→ 비용 낮음!

⚠️ 핵심 정리:

  • 페이지: 가상 메모리를 나눈 고정 크기 단위 (일반적으로 4KB)
  • 페이지 테이블: 가상 주소 → 물리 주소 변환 매핑 테이블
  • MMU: CPU 내부 하드웨어, 가상 주소를 물리 주소로 변환
  • TLB: MMU 내부 캐시, 페이지 테이블 조회 속도 향상
  • 페이지 폴트: 페이지가 물리 메모리에 없을 때 발생
  • 프로세스: 독립적인 페이지 테이블 (컨텍스트 스위칭 비용 높음)
  • 스레드: 같은 페이지 테이블 공유 (컨텍스트 스위칭 비용 낮음)

⚙️ 3. 스레드 스케줄링

스케줄링이란?

스케줄링은 "CPU를 어떤 스레드에게 할당할지 결정하는 것"입니다.

⚠️ 핵심: CPU 코어 수보다 스레드 수가 많은 것은 정상적인 상황입니다!

왜 스케줄링이 필요한가요?

일반적인 상황:

  • CPU 코어 수: 4개 (예: 4코어 CPU)
  • 실행 중인 스레드 수: 수십 ~ 수백 개
  • CPU 코어 수 < 실행 중인 스레드 수 ← 정상적인 상황!

예시:

CPU: 4코어
실행 중인 스레드: 100개

→ 4개의 코어로 100개의 스레드를 실행해야 함
→ 한 번에 4개만 실행 가능
→ 나머지 96개는 대기
→ 스케줄러가 번갈아가며 실행

스케줄링이 필요한 이유:

  1. CPU 코어 수 < 실행 중인 스레드 수 (정상적인 상황)
  2. 여러 스레드가 번갈아가며 실행되어야 함
  3. CPU 시간을 공평하게 분배해야 함
  4. 모든 스레드가 실행 기회를 가져야 함

비유:

  • CPU = 도서관 열람실 (좌석 4개)
  • 스레드 = 이용자들 (100명)
  • 스케줄러 = 좌석 배정 관리자 (4명씩 번갈아가며 사용)

스케줄링 방식

1. 선점형 스케줄링 (Preemptive Scheduling)

운영체제가 강제로 CPU를 빼앗는 방식

특징:

  • 시간 할당량(Time Quantum)이 있음
  • 시간이 지나면 다른 스레드에게 CPU를 넘김
  • 공평한 CPU 사용 보장
  • 대부분의 현대 OS가 사용

예시:

스레드1 실행 (10ms) → 스레드2 실행 (10ms) → 스레드3 실행 (10ms) → 반복

2. 비선점형 스케줄링 (Non-Preemptive Scheduling)

스레드가 자발적으로 CPU를 반납하는 방식

특징:

  • 스레드가 끝날 때까지 CPU를 사용
  • 다른 스레드가 오래 기다릴 수 있음
  • 공평하지 않을 수 있음

스케줄링 알고리즘

Round Robin (라운드 로빈)

시간 할당량을 정해서 순환하는 방식

스레드1 (10ms) → 스레드2 (10ms) → 스레드3 (10ms) → 스레드1 (10ms) → ...

특징:

  • 공평한 CPU 분배
  • 응답 시간이 짧음
  • 대화형 프로그램에 적합

Priority Scheduling (우선순위 스케줄링)

우선순위가 높은 스레드부터 실행

우선순위 높음: 스레드1 → 스레드2 → 스레드3
우선순위 낮음: 스레드4 → 스레드5

특징:

  • 중요한 작업을 먼저 처리
  • 우선순위가 낮은 스레드는 오래 기다릴 수 있음

🔄 4. 컨텍스트 스위칭 (Context Switching)

컨텍스트 스위칭이란?

컨텍스트 스위칭은 "한 스레드에서 다른 스레드로 CPU를 넘기는 과정"입니다.

⚠️ 핵심: CPU 코어 수보다 스레드 수가 많기 때문에 컨텍스트 스위칭이 필요합니다!

왜 필요한가요?

일반적인 상황:

  • CPU 코어 수: 4개
  • 실행 중인 스레드 수: 100개
  • 한 번에 4개만 실행 가능 → 나머지는 대기
  • 대기 중인 스레드도 실행 기회를 가져야 함 → 컨텍스트 스위칭 필요

컨텍스트 스위칭이 필요한 이유:

  1. CPU 코어 수 < 실행 중인 스레드 수 (정상적인 상황)
  2. 여러 스레드가 번갈아가며 실행되어야 함
  3. 각 스레드가 공평하게 CPU를 사용해야 함
  4. 모든 스레드가 실행 기회를 가져야 함

비유:

  • 도서관에서 좌석을 다른 사람에게 넘기는 것
  • 현재 사용자의 책상 상태를 저장하고, 다음 사용자의 책상 상태를 복원

컨텍스트 스위칭 과정

1. 현재 스레드 상태 저장

CPU 레지스터 값 저장:
  - PC (Program Counter): 현재 실행 중인 명령어 주소
  - SP (Stack Pointer): 스택 포인터
  - 레지스터 값들

2. 다음 스레드 상태 복원

CPU 레지스터 값 복원:
  - PC: 다음 스레드의 명령어 주소
  - SP: 다음 스레드의 스택 포인터
  - 레지스터 값들

3. 스레드 전환

스레드1 실행 중
  ↓
컨텍스트 스위칭 (스레드1 상태 저장)
  ↓
스레드2 상태 복원
  ↓
스레드2 실행 시작

컨텍스트 스위칭 비용

컨텍스트 스위칭은 비용이 듭니다:

  1. 레지스터 저장/복원

    • CPU 레지스터 값들을 메모리에 저장
    • 다음 스레드의 레지스터 값들을 메모리에서 복원

  2. 캐시 미스

    • 다른 스레드로 전환되면 캐시가 무효화될 수 있음
    • 메모리 접근이 느려짐

  3. 스케줄러 오버헤드

    • 다음에 실행할 스레드를 선택하는 비용

⚠️ 프로세스 컨텍스트 스위칭 vs 스레드 컨텍스트 스위칭

두 가지는 완전히 다릅니다!

프로세스 컨텍스트 스위칭

프로세스 간 전환 시:

1. 현재 프로세스의 레지스터 값 저장
2. 메모리 공간 전환 (페이지 테이블 전환)
   - 프로세스 A의 가상 주소 공간 → 프로세스 B의 가상 주소 공간
3. 다음 프로세스의 레지스터 값 복원
4. 캐시 무효화 (다른 메모리 공간이므로)

비용이 높은 이유:

  • 메모리 공간 전환이 필요 (페이지 테이블 전환)
  • 캐시가 완전히 무효화됨
  • TLB (Translation Lookaside Buffer) 플러시 필요

비용: 높음 (수십 ~ 수백 마이크로초)

스레드 컨텍스트 스위칭

같은 프로세스 내 스레드 간 전환 시:

1. 현재 스레드의 레지스터 값 저장
2. 스택 포인터만 전환 (메모리 공간 전환 없음!)
   - 같은 프로세스 내이므로 메모리 공간은 그대로
3. 다음 스레드의 레지스터 값 복원
4. 캐시는 부분적으로 유효 (같은 메모리 공간)

비용이 낮은 이유:

  • 메모리 공간 전환 불필요 (같은 프로세스 내)
  • 스택 포인터만 변경하면 됨
  • 캐시가 부분적으로 유효함

비용: 낮음 (수 마이크로초)

비용 비교:

프로세스 컨텍스트 스위칭: 높음 (메모리 공간 전환)
스레드 컨텍스트 스위칭: 낮음 (스택만 전환)

비유:

  • 프로세스 스위칭: 다른 아파트로 이사 (모든 가구 이동, 주소 변경)
  • 스레드 스위칭: 같은 아파트 안에서 방만 바꿈 (가벼운 이동, 주소 그대로)

예시:

프로세스 A (스레드1) → 프로세스 B (스레드1):
  - 메모리 공간 전환 필요
  - 페이지 테이블 전환
  - 캐시 무효화
  → 비용 높음

프로세스 A (스레드1) → 프로세스 A (스레드2):
  - 메모리 공간 전환 불필요 (같은 프로세스)
  - 스택 포인터만 변경
  - 캐시 부분 유효
  → 비용 낮음

🔒 5. 스레드 동기화

동기화(Synchronization)란?

⚠️ 동기화는 "여러 스레드가 공유 자원에 접근할 때, 한 번에 하나의 스레드만 접근하도록 제어하는 것"입니다.

핵심 개념:

  • 동기화 = 순서 제어 + 상호 배제
  • 여러 스레드가 동시에 접근하면 문제 발생
  • 동기화를 통해 안전하게 접근하도록 제어

비유:

  • 동기화 없이: 여러 사람이 동시에 화장실 사용 (충돌!)
  • 동기화 후: 한 번에 한 사람만 화장실 사용 (안전!)

동기화가 왜 필요한가요?

여러 스레드가 공유 메모리에 동시에 접근하면 문제가 발생할 수 있습니다.

문제 상황:

class Counter {
    private int count = 0;
    
    public void increment() {
        count++;  // 여러 스레드가 동시에 실행하면?
    }
}

경쟁 조건 (Race Condition):

스레드1: count 읽기 (0)
스레드2: count 읽기 (0)
스레드1: count++ (1)
스레드2: count++ (1)
→ 결과: 1 (하지만 2가 되어야 함!)

동기화 메커니즘

1. 뮤텍스 (Mutex)

상호 배제 (Mutual Exclusion) - 한 번에 하나의 스레드만 접근

비유:

  • 화장실 열쇠 (한 번에 한 사람만 사용 가능)
  • 열쇠를 가진 사람만 화장실 사용 가능

동작:

스레드1: 뮤텍스 획득 → 작업 수행 → 뮤텍스 해제
스레드2: 뮤텍스 대기 → 뮤텍스 획득 → 작업 수행 → 뮤텍스 해제

2. 세마포어 (Semaphore)

여러 스레드가 동시에 접근할 수 있도록 허용 (개수 제한)

비유:

  • 주차장 (여러 대 동시 주차 가능, 하지만 개수 제한)
  • 주차 공간이 있으면 입장, 없으면 대기

동작:

세마포어(3): 최대 3개 스레드 동시 접근 가능
스레드1, 2, 3: 동시 접근 가능
스레드4: 대기 (공간이 생길 때까지)

⚠️ 중요한 질문: 세마포어 카운터 관리에서 동시성 이슈가 발생하지 않나요?

답: 원자적 연산(Atomic Operation)으로 해결합니다!

문제 상황 (원자적 연산 없이):

// 세마포어 카운터 관리 (의사코드)
int count = 3;  // 세마포어 카운터

// 스레드1과 스레드2가 동시에 접근 시도
스레드1: count 읽기 (3)
스레드2: count 읽기 (3)  // 동시에 읽음!
스레드1: count-- (2)
스레드2: count-- (2)  // 둘 다 감소시킴
→ 결과: count = 2 (하지만 1이 되어야 함!)
→ 동시성 이슈 발생! 💥

해결책: 원자적 연산 (Atomic Operation)

세마포어는 원자적 연산을 사용합니다:

원자적 연산 (Atomic Operation):
  - 읽기 + 감소를 한 번에 수행
  - 중간에 다른 스레드가 끼어들 수 없음
  - CPU 레벨에서 보장됨

스레드1: 원자적 연산 (count 읽기 + 감소) → count = 2
스레드2: 원자적 연산 (count 읽기 + 감소) → count = 1
→ 정상 동작! ✅

세마포어의 내부 구현:

세마포어 카운터 관리:
  - 원자적 연산 사용 (compare-and-swap 등)
  - CPU 레벨에서 보장
  - 동시성 이슈 없음

비유:

  • 일반 연산: 여러 사람이 동시에 계산기 사용 (충돌 가능)
  • 원자적 연산: 계산기가 한 번에 한 사람만 사용 가능 (충돌 불가능)

⚠️ 핵심:

  • 세마포어 자체는 원자적 연산으로 구현되어 있어서 안전함
  • 하지만 세마포어로 보호하는 공유 자원은 여전히 동기화 필요할 수 있음
  • 세마포어는 "접근 개수 제한"만 보장, 공유 자원의 안전성은 별도로 보장해야 함

3. 모니터 (Monitor)

뮤텍스 + 조건 변수 (Condition Variable)

⚠️ 모니터는 "뮤텍스로 상호 배제 + 조건 변수로 스레드 간 통신"을 제공하는 고수준 동기화 메커니즘입니다.

구성 요소:

  1. 뮤텍스: 상호 배제 (한 번에 하나의 스레드만 접근)
  2. 조건 변수 (Condition Variable): 스레드 간 통신 (조건이 만족될 때까지 대기)

왜 필요한가요?

뮤텍스만으로는 부족한 경우:

// 뮤텍스만 사용하면?
synchronized (lock) {
    while (queue.isEmpty()) {
        // 큐가 비어있으면 대기해야 하는데...
        // 뮤텍스만으로는 다른 스레드가 알려줄 수 없음!
    }
    // 큐에서 데이터 가져오기
}

모니터를 사용하면:

// 모니터 사용 (Java의 synchronized + wait/notify)
synchronized (lock) {
    while (queue.isEmpty()) {
        lock.wait();  // 조건 변수: 큐가 비어있으면 대기
    }
    // 큐에서 데이터 가져오기
}

// 다른 스레드에서
synchronized (lock) {
    queue.add(data);
    lock.notify();  // 조건 변수: 대기 중인 스레드에게 알림
}

동작 방식:

1. 뮤텍스 획득 (상호 배제)
2. 조건 확인
   - 조건 만족 → 작업 수행
   - 조건 불만족 → 조건 변수로 대기 (뮤텍스 자동 해제)
3. 다른 스레드가 조건 만족 시 알림
4. 대기 중인 스레드 깨움
5. 뮤텍스 재획득 후 작업 수행

비유:

  • 뮤텍스: 화장실 열쇠 (한 번에 한 사람만 사용)
  • 조건 변수: 알림벨 (화장실이 비면 알림)
  • 모니터: 화장실 열쇠 + 알림벨 (조합)

실제 예시:

// 생산자-소비자 패턴
class Buffer {
    private Queue<Integer> queue = new LinkedList<>();
    private final Object lock = new Object();
    
    // 소비자
    public Integer take() {
        synchronized (lock) {
            while (queue.isEmpty()) {
                try {
                    lock.wait();  // 조건 변수: 큐가 비어있으면 대기
                } catch (InterruptedException e) {
                    // ...
                }
            }
            return queue.poll();
        }
    }
    
    // 생산자
    public void put(Integer item) {
        synchronized (lock) {
            queue.add(item);
            lock.notify();  // 조건 변수: 대기 중인 스레드에게 알림
        }
    }
}

⚠️ 핵심:

  • 모니터 = 뮤텍스 + 조건 변수
  • 뮤텍스: 상호 배제 보장
  • 조건 변수: 조건이 만족될 때까지 대기하고, 만족되면 알림
  • Java의 synchronized + wait()/notify()가 모니터 패턴

📊 6. 스레드의 장단점

장점

  1. 응답성 향상

    • UI 스레드가 블로킹되어도 다른 스레드가 작업 수행
    • 사용자 경험 개선

  2. 자원 공유

    • 같은 프로세스 내에서 메모리 공유
    • 통신 비용 감소

  3. 경제성

    • 프로세스 생성보다 스레드 생성이 저렴
    • 컨텍스트 스위칭 비용이 낮음

  4. 멀티코어 활용

    • 여러 CPU 코어를 동시에 사용
    • 성능 향상

단점

  1. 동기화 문제

    • 공유 메모리 접근 시 동기화 필요
    • 데드락, 경쟁 조건 등 문제 발생 가능

  2. 디버깅 어려움

    • 여러 스레드가 동시에 실행되어 추적이 어려움
    • 타이밍에 의존하는 버그 발생

  3. 안정성 문제

    • 한 스레드가 죽으면 전체 프로세스에 영향
    • 프로세스보다 취약함

🎓 핵심 정리

1. ⚠️ 프로세스와 스레드의 관계

  • 프로세스: 메모리 공간을 가진 컨테이너
  • 스레드: 프로세스 내에서 실제 작업을 수행하는 실행 단위
  • 관계: 프로세스 안에 스레드가 존재 (포함 관계)
  • 핵심: 프로세스가 돌아가게 하는 것은 스레드!

2. ⚠️ 스레드의 메모리 구조

  • 공유: Code, Data, Heap
  • 독립: 각 스레드의 Stack

3. ⚠️ 스케줄링

  • CPU 시간을 여러 스레드에 분배
  • Round Robin, Priority Scheduling 등

4. ⚠️ 컨텍스트 스위칭

  • 한 스레드에서 다른 스레드로 CPU 전환
  • 레지스터 저장/복원 비용 발생

5. ⚠️ 동기화

  • 공유 메모리 접근 시 동기화 필요
  • 뮤텍스, 세마포어, 모니터 등 사용
