6년차에 접어들고보니 내가 잘 알고 있는게 맞나 라는 의구심이 들었고, Java 를 다시 한 번 되짚어 보는 시간을 가지고 있습니다. 그 중 JVM에 대해 정리하다 보니, "가상머신"이라는 개념이 무엇인지, 그리고 JVM이 왜 프로세스 가상머신으로 분류되는지 과연 내가 알고 쓰고 있는 것인지 확인하고 싶어졌어요.

가상머신은 크게 시스템 가상머신과 프로세스 가상머신으로 나뉘는데, 이 둘의 차이와 실제 개발 환경에서의 활용을 정리해봤어요.

가상머신이란?

가상머신(Virtual Machine, VM)은 물리적 하드웨어를 소프트웨어로 추상화한 실행 환경이에요. 실제 물리적 머신(CPU, 메모리, 디스크)이 아닌 소프트웨어로 구현된 머신으로, 하드웨어를 추상화하여 다른 환경을 제공해요.

가상머신의 핵심은:

  • 추상화: 물리적 하드웨어의 복잡성을 숨기고 일관된 인터페이스 제공
  • 격리: 여러 실행 환경을 물리적으로 분리하지 않고 논리적으로 분리
  • 자원 가상화: 하나의 물리적 자원을 여러 가상 자원으로 분할
  • 자원 활용도 향상: 하나의 물리적 서버에서 여러 VM을 운영하여 하드웨어 자원 활용률을 높임

가상머신은 구현 방식과 목적에 따라 크게 두 가지로 분류돼요:

시스템 가상머신 (System Virtual Machine)

시스템 가상머신은 전체 운영체제를 가상화하여 물리적 하드웨어를 완전히 추상화해요. Guest OS가 완전한 운영체제 환경을 제공하며, CPU, 메모리, 디스크, 네트워크 등 모든 하드웨어를 가상화해요. 하나의 물리적 서버에 여러 다른 OS를 동시에 실행할 수 있고, 각 VM은 독립적인 실행 환경을 가져요.

하이퍼바이저를 통해 물리적 하드웨어를 가상화하여 여러 운영체제를 동시에 실행할 수 있으며, 이를 통해 서버 통합(Server Consolidation)과 자원 효율성을 높일 수 있어요.

하이퍼바이저

하이퍼바이저는 시스템 가상머신의 핵심 구성 요소로, 물리적 하드웨어와 가상 머신 사이의 중간 계층이에요. VMM (Virtual Machine Monitor)이라고도 불려요. 물리 서버에서 작동하는 소프트웨어로, VM이나 펌웨어, 소프트웨어를 구축하고 운영해줘요.

하이퍼바이저의 주요 역할은:

  • 리소스 관리: 물리적 하드웨어(CPU, 메모리, 디스크, 네트워크)를 여러 VM에 분배
  • 격리 보장: 각 VM이 독립적으로 실행되도록 격리
  • 가상화 제공: Guest OS가 실제 하드웨어를 직접 접근하지 않고 가상화된 하드웨어를 사용하도록 함

Windows를 사용하는 분들은 WSL2를 사용하기 위해 이 옵션을 다뤄본 적이 있을 거예요.

하이퍼바이저는 두 가지 타입으로 나뉘는데요:

Type 1: Native/Bare-Metal Hypervisor

물리적 하드웨어에 직접 설치되며, Host OS 없이 하이퍼바이저가 직접 하드웨어를 제어해요. 성능 오버헤드가 적어서 엔터프라이즈 환경에서 주로 사용돼요.

구조:

┌─────────────────────────────────┐
│  Guest OS 1 (Windows)           │
│  Guest OS 2 (Linux)             │
│  Guest OS 3 (macOS)             │
├─────────────────────────────────┤
│  Hypervisor (VMware ESXi, KVM)  │  ← 하드웨어 직접 제어
├─────────────────────────────────┤
│  물리적 하드웨어                    │
└─────────────────────────────────┘

대표적인 예:

  • VMware ESXi: 엔터프라이즈 서버 가상화
  • Microsoft Hyper-V: Windows Server 가상화 (일반적으로 Type 1로 분류, Windows Server 위에서 실행 시 Type 2 특성도 가짐)
  • KVM: Linux 기반 오픈소스
  • Xen: 오픈소스 하이퍼바이저

Type 1 하이퍼바이저는 베어메탈(Bare-Metal) 하이퍼바이저라고도 불리며, 하드웨어에 직접 설치되어 성능과 보안 측면에서 우수해요. 데이터센터 서버 통합, 클라우드 인프라(AWS EC2, Azure VM), 엔터프라이즈 서버 가상화에 주로 사용돼요.

Type 2: Hosted Hypervisor

Host OS 위에 설치되며, Host OS가 하드웨어를 제어하고 하이퍼바이저가 그 위에서 동작해요. Type 1보다 성능 오버헤드가 크지만 설치와 사용이 간단해요.

구조:

┌─────────────────────────────────┐
│  Guest OS 1 (Linux)             │
│  Guest OS 2 (Windows)           │
├─────────────────────────────────┤
│  Hypervisor (VMware, VirtualBox)│
├─────────────────────────────────┤
│  Host OS (Windows/Mac/Linux)    │  ← 호스트 운영체제
├─────────────────────────────────┤
│  물리적 하드웨어                    │
└─────────────────────────────────┘

대표적인 예:

  • VMware Workstation: 데스크톱 가상화
  • VirtualBox: 오픈소스 데스크톱 가상화
  • Parallels Desktop: Mac에서 Windows 실행

Type 2 하이퍼바이저는 호스팅된(Hosted) 하이퍼바이저라고도 불리며, 개발 환경 구축, 테스트 환경 분리, 데스크톱에서 여러 OS 사용에 적합해요.

컨테이너와의 관계

컨테이너는 OS 레벨 가상화 기술로, 시스템 가상머신과는 다른 접근 방식을 사용해요. 전통적인 시스템 VM은 하드웨어를 가상화하지만, 컨테이너는 호스트 OS의 커널을 공유하면서 애플리케이션 레벨에서 격리를 제공해요.

아키텍처 차이: Hypervisor vs Container Engine

가장 근본적인 차이점은 가상화를 어느 수준에서, 어떤 방식으로 수행하는가예요.

VM 아키텍처: 하드웨어 가상화

  • 하드웨어 계층을 가상화하는 방식
  • 하이퍼바이저가 물리적 하드웨어를 소프트웨어적으로 에뮬레이션
  • 각 VM이 독립된 가상 컴퓨터처럼 동작
  • Guest OS가 완전한 운영체제 환경을 가짐

컨테이너 아키텍처: 운영체제 수준 가상화

  • 운영체제 계층을 가상화하는 방식
  • Container Engine(Docker Engine 등)이 호스트 OS 커널을 공유
  • Namespaces와 cgroups를 통해 프로세스 격리
  • 애플리케이션과 그 종속성만 패키징

핵심 차이점:

  • VM: 하드웨어 수준의 가상화로, 각 VM이 자체 운영체제를 실행해요. 하이퍼바이저가 물리적 하드웨어를 가상화하여 여러 Guest OS를 실행할 수 있게 해요.
  • 컨테이너: 운영체제 수준의 가상화로, 호스트 OS 커널을 공유하면서 애플리케이션과 그 종속성을 격리된 환경에서 실행해요. Docker Engine이 컨테이너 런타임을 관리해요.

VM 아키텍처 구조:

┌─────────────────────────────────┐
│  Guest OS 1 (완전한 OS)           │
│  Guest OS 2 (완전한 OS)           │
├─────────────────────────────────┤
│  Hypervisor (하드웨어 가상화)       │  ← 하드웨어 에뮬레이션
├─────────────────────────────────┤
│  Host OS (Type 2인 경우)          │
├─────────────────────────────────┤
│  물리적 하드웨어                    │
└─────────────────────────────────┘

컨테이너 아키텍처 구조:

┌─────────────────────────────────┐
│  Container 1 (App + Libs)       │
│  Container 2 (App + Libs)       │
│  Container 3 (App + Libs)       │
├─────────────────────────────────┤
│  Container Engine (Docker 등)    │  ← Namespaces, cgroups
├─────────────────────────────────┤
│  Host OS (Linux Kernel)         │  ← OS 커널 공유
├─────────────────────────────────┤
│  물리적 하드웨어                    │
└─────────────────────────────────┘

컨테이너는 Namespaces와 **cgroups(Control Groups)**를 통해 프로세스를 격리해요. Namespaces는 프로세스가 보는 리소스(파일 시스템, 네트워크, 프로세스 ID 등)를 격리하고, cgroups는 CPU, 메모리, 디스크 I/O 등의 리소스 사용량을 제한해요.

왜 이런 차이가 생길까요?

VM은 하이퍼바이저를 통해 물리적 하드웨어를 가상화하기 때문에, 각 VM마다 완전한 운영체제가 필요해요. 하이퍼바이저가 물리적 하드웨어를 소프트웨어적으로 에뮬레이션하여 여러 개의 독립된 가상 컴퓨터를 만드는 개념이에요.

반면 컨테이너는 Container Engine이 호스트 OS 커널을 공유하면서, Namespaces와 **cgroups(Control Groups)**를 통해 프로세스를 격리해요. Namespaces는 프로세스가 보는 리소스(파일 시스템, 네트워크, 프로세스 ID 등)를 격리하고, cgroups는 CPU, 메모리, 디스크 I/O 등의 리소스 사용량을 제한해요. 이로 인해 컨테이너는 VM보다 훨씬 가볍고 빠르게 실행될 수 있어요.

언제 무엇을 사용할까요?

컨테이너가 적합한 경우:

  • 마이크로서비스 아키텍처: 경량이고 빠른 시작 시간이 중요해요
  • 클라우드 네이티브 애플리케이션: 확장성과 이식성이 중요해요
  • CI/CD 파이프라인: 빠른 빌드와 배포가 필요해요
  • 개발/테스트 환경: 빠르게 환경을 구축하고 정리해야 해요

VM이 적합한 경우:

  • 완전한 격리가 필요한 경우: 보안이 중요한 환경
  • 다양한 OS가 필요한 경우: Windows, Linux 등 서로 다른 OS를 동시에 실행
  • 레거시 시스템 마이그레이션: 기존 시스템을 그대로 가상화
  • 클라우드 인프라 제공: 여러 고객에게 격리된 환경 제공

실무에서는 마이크로서비스 아키텍처에는 컨테이너가 더 적합하고(경량, 빠른 시작), 레거시 시스템처럼 완전한 격리가 필요한 경우에는 전통적인 VM이 더 적합해요. 클라우드 네이티브 환경에서는 컨테이너 기반 배포가 표준이에요.

격리 수준의 차이

순수하게 격리의 강도만을 놓고 본다면, 독립된 커널을 사용하는 VM이 커널을 공유하는 컨테이너보다 더 강력한 격리 수준을 제공해요. 하지만 컨테이너가 제공하는 운영체제 수준의 격리도 대부분의 일반적인 애플리케이션 환경에서는 충분한 수준의 보안과 안정성을 제공할 수 있어요.

특히 SELinux/AppArmor, Seccomp, Capabilities, User Namespaces 등 다양한 보안 강화 기법들을 함께 적용하면 컨테이너의 격리 수준을 더욱 높일 수 있어요. 또한 gVisor(커널 시스템 콜을 사용자 공간에서 가로채어 처리)나 Kata Containers(각 컨테이너를 경량화된 VM 위에서 실행) 같은 기술들은 약간의 성능 오버헤드를 감수하는 대신 하드웨어 가상화 수준의 격리를 제공해요.

결국 어떤 기술을 선택할지는 워크로드의 특성, 보안 요구사항, 운영체제 환경, 관리 복잡성 및 비용 효율성 등을 종합적으로 고려해야 해요.

실제 사용 사례

  1. 서버 통합: 물리 서버 10대를 가상 서버 100대로 통합하여 하드웨어 자원 활용률을 높이고 운영 비용을 절감
  2. 클라우드 인프라: AWS EC2, Azure VM, GCP Compute Engine 등에서 여러 고객이 같은 물리 서버를 공유하면서 자원 격리와 보안 보장
  3. 개발/테스트 환경: 프로덕션 환경과 동일한 환경 구축, 여러 버전의 OS/소프트웨어 테스트, 환경 분리로 안전한 테스트

실제 테스트: VM vs 컨테이너 리소스 비교

실제로 VM과 Docker 컨테이너를 만들어서 리소스 사용량을 측정해봤어요. 직접 해보시면 차이를 확실히 느낄 수 있을 거예요.

참고: VirtualBox는 버전 7.1부터 Apple Silicon Mac을 지원하지만, 일부 제한사항이 있을 수 있어요. Apple Silicon Mac 사용자는 UTM, Parallels Desktop, VMware Fusion 같은 대안도 고려해볼 수 있어요.

테스트 환경:

  • Host OS: macOS Sonoma 14.1
  • CPU: Apple M1 Pro
  • RAM: 16GB

참고: Ubuntu 22.04 LTS를 선택한 이유는 LTS(Long Term Support) 버전이라 안정적이고, 널리 사용되는 버전이기 때문이에요. 다른 버전(20.04, 24.04 등)이나 다른 OS 이미지(Alpine, Debian 등)를 사용해도 비교 테스트는 가능해요.

VM 테스트

참고: VirtualBox는 버전 7.1부터 Apple Silicon Mac을 지원하기 시작했어요. (Oracle VirtualBox 7.1 공식 발표) 하지만 일부 기능이 제한적이거나 성능 저하가 있을 수 있어요. Apple Silicon Mac에서는 UTM, Parallels Desktop, VMware Fusion 같은 대안도 고려해볼 수 있어요.

VirtualBox가 설치되어 있다면:

# VM 시작 시간 측정 (VirtualBox CLI 사용)
$ time VBoxManage startvm "Ubuntu-VM" --type headless
real    0m35.456s  # 약 35초

# VM 메모리 할당 확인
$ VBoxManage showvminfo "Ubuntu-VM" | grep Memory
Memory size: 2048MB

# VM 디스크 크기 확인
$ VBoxManage showvminfo "Ubuntu-VM" | grep "Storage"

또는 VirtualBox GUI에서 VM을 시작하고 Activity Monitor(맥) 또는 Task Manager(윈도우)로 메모리 사용량을 확인할 수 있어요.

Apple Silicon Mac 사용자를 위한 대안:

VirtualBox 대신 다음 도구들도 사용할 수 있어요:

  1. UTM (무료, 오픈소스)

    • App Store에서 설치 가능
    • QEMU 기반으로 다양한 OS 지원
    • 설치 및 사용이 간단해요

  2. Parallels Desktop (유료)

    • Apple Silicon 최적화
    • 성능이 우수하고 사용이 편리해요

  3. VMware Fusion (유료, 개인 사용 무료)

    • Apple Silicon 지원
    • 엔터프라이즈 환경에서 많이 사용해요

VM 테스트는 선택 사항이에요. Docker 컨테이너 테스트만으로도 VM과 컨테이너의 차이를 충분히 확인할 수 있어요.

결과:

메모리 사용량2GB (할당)약 0.7MB (712KiB)

참고: VirtualBox는 버전 7.1부터 Apple Silicon Mac을 지원하지만, 일부 제한사항이 있을 수 있어요. Apple Silicon Mac 사용자는 UTM, Parallels Desktop, VMware Fusion 같은 대안도 고려해볼 수 있어요. VM 테스트는 선택 사항이며, Docker 컨테이너 테스트만으로도 차이를 충분히 확인할 수 있어요.

VM은 전체 OS를 포함하므로 리소스 사용량이 크지만, 컨테이너는 호스트 OS 커널을 공유하므로 훨씬 가벼워요. 직접 테스트해보시면 이 차이를 확실히 느낄 수 있을 거예요.

실무 활용

개발 환경

로컬 개발 환경에서는 Docker(컨테이너)로 마이크로서비스 개발과 의존성 격리를 해요. 여러 OS 환경 테스트가 필요할 때는 가상머신을 사용하죠.

CI/CD 파이프라인에서는 컨테이너로 빌드 및 배포 환경을 표준화해요.

프로덕션 환경에서는 클라우드 VM(AWS EC2, Azure VM 등)을 사용하고, 컨테이너 오케스트레이션(Kubernetes)을 활용해요.

성능 최적화

시스템 VM 최적화는 하이퍼바이저 타입 선택(Type 1 vs Type 2), CPU/메모리 오버커밋 설정, 네트워크/디스크 I/O 최적화로 진행해요.

정리

시스템 가상머신은 전체 OS를 가상화하여 하드웨어를 추상화해요. 하이퍼바이저 기반(Type 1, Type 2)으로 동작하며, 예로는 VMware, AWS EC2가 있어요.

컨테이너는 OS 레벨 가상화 기술로, 시스템 가상머신과는 다른 접근 방식을 사용해요. 호스트 OS 커널을 공유하면서 Namespaces와 cgroups를 통해 프로세스를 격리해요.

VM과 컨테이너는 각각의 장단점이 있어서, 워크로드의 특성과 요구사항에 따라 선택해야 해요. 클라우드 네이티브 환경에서는 컨테이너가 표준이지만, 완전한 격리가 필요한 경우에는 VM이 더 적합해요.
