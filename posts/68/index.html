안녕하세요. 이번 파트에서는 직렬화된 바이트 스트림이 어떻게 다시 객체로 복원되는지, 그 과정에서 어떤 함정이 있는지를 다룹니다.

Part 1에서 Point(1, 2)를 직렬화하면 클래스 이름, 필드 이름, 타입 코드까지 모두 바이트에 박힌다는 것을 봤습니다. 이번에는 그 바이트를 ObjectInputStream이 받았을 때 어떻게 읽어서 객체를 만드는지를 따라가 보겠습니다. 그리고 이 구조가 만들어내는 몇 가지 불편한 진실도 함께 마주하겠습니다.

🔄 1. ObjectInputStream은 어떤 순서로 읽는가

역직렬화는 직렬화의 역순입니다. ObjectInputStream.readObject()를 호출하면 이런 순서로 진행됩니다.

ObjectInputStream ois = new ObjectInputStream(new ByteArrayInputStream(bytes));
Point point = (Point) ois.readObject();

내부적으로 스트림을 앞에서부터 읽어나갑니다.

AC ED → STREAM_MAGIC 확인. 이 값이 아니면 즉시 StreamCorruptedException
00 05 → STREAM_VERSION 확인
73    → TC_OBJECT: 객체 하나를 읽겠다
72    → TC_CLASSDESC: 클래스 설명 블록 시작

클래스 이름을 읽으면 Class.forName()으로 현재 ClassLoader에서 해당 클래스를 찾습니다.

// ObjectInputStream 내부 (단순화)
String className = readUTF(); // "Point"
Class<?> cl = Class.forName(className, false, latestUserDefinedLoader());

클래스를 찾으면 스트림에 기록된 serialVersionUID와 현재 클래스의 serialVersionUID를 비교합니다. 일치하면 계속 진행하고, 불일치하면 즉시 예외를 던집니다. 이 부분이 나중에 꽤 골치 아픈 상황을 만들기도 합니다.

이어서 필드 목록을 읽고, 스트림에 기록된 필드와 현재 클래스의 필드를 매핑합니다. 그 다음 객체를 생성하고 필드 값을 채웁니다.

🏗️ 2. 생성자가 호출되지 않는다

역직렬화에서 가장 당황스러운 부분이 여기입니다. 객체를 만드는데 생성자가 실행되지 않습니다.

public class User implements Serializable {
    String name;
    int age;

    public User(String name, int age) {
        if (age < 0) throw new IllegalArgumentException("나이는 음수일 수 없습니다");
        this.name = name;
        this.age = age;
    }
}

이 클래스를 역직렬화하면 new User(name, age)가 아니라 sun.reflect.ReflectionFactory를 통해 생성자를 완전히 우회한 객체가 만들어집니다.

// ObjectInputStream 내부에서 실제로 벌어지는 일 (단순화)
ReflectionFactory rf = ReflectionFactory.getReflectionFactory();
Constructor<?> objDef = Object.class.getDeclaredConstructor();
Constructor<?> intConstr = rf.newConstructorForSerialization(User.class, objDef);
User user = (User) intConstr.newInstance(); // User 생성자는 실행되지 않습니다

Object의 기본 생성자만 호출하고, User의 생성자는 건너뜁니다. 그 뒤 리플렉션으로 필드에 값을 직접 주입합니다.

이것이 의미하는 바는 이렇습니다. 생성자에서 아무리 꼼꼼하게 유효성 검사를 해두어도, 역직렬화 경로로 들어오는 객체는 그 검사를 전혀 거치지 않습니다. age = -1인 User 객체가 만들어질 수 있습니다.

직렬화를 지원하는 클래스를 설계할 때 생성자 유효성 검사를 맹신하면 안 되는 이유가 여기 있습니다.

🔑 3. serialVersionUID가 실제로 하는 일

serialVersionUID를 선언하지 않으면 IDE에서 노란 경고가 뜹니다. 관성적으로 1L을 넣어왔는데, 이게 정확히 무슨 역할을 하는지 짚어보겠습니다.

직렬화 스트림에는 8바이트짜리 serialVersionUID가 기록됩니다. 역직렬화 시 스트림의 UID와 현재 클래스의 UID가 다르면 이 예외가 발생합니다.

java.io.InvalidClassException: User; local class incompatible:
stream classdesc serialVersionUID = 8683452581122892189,
local class serialVersionUID = -6849794470754667710

선언하지 않으면 JVM이 자동으로 계산하는데, 계산 기준이 까다롭습니다.

// serialVersionUID 자동 계산에 포함되는 요소들
// - 클래스 이름
// - 구현한 인터페이스 목록 (알파벳 순)
// - 필드 이름과 타입 (static, transient 포함)
// - 생성자 시그니처
// - 메서드 이름과 시그니처 (알파벳 순)

메서드를 하나 추가했을 뿐인데 UID가 바뀝니다. 데이터는 전혀 바뀌지 않았지만 역직렬화가 실패합니다. 리팩토링 한 번에 저장된 세션이나 캐시가 전부 날아갈 수 있습니다.

// 이것만 추가해도 자동 계산 UID가 바뀝니다
public String getDisplayName() {
    return name + " (" + age + ")";
}

그래서 명시적으로 선언하는 것이 권장됩니다.

public class User implements Serializable {
    private static final long serialVersionUID = 1L; // 명시적 선언

    String name;
    int age;
}

UID를 고정하면 클래스 구조가 바뀌어도 역직렬화는 시도합니다. 단, 필드가 삭제되거나 타입이 바뀌면 InvalidClassException 대신 다른 문제가 생길 수 있으니, UID가 같다고 해서 항상 안전한 것은 아닙니다.

🚫 4. transient — 직렬화에서 제외하기

모든 필드를 직렬화할 필요는 없습니다. 아니, 해서는 안 되는 필드도 있습니다.

public class UserSession implements Serializable {
    private static final long serialVersionUID = 1L;

    String userId;
    String token;

    transient String password;           // 민감 정보 — 직렬화 제외
    transient Connection dbConnection;   // Connection은 Serializable이 아님
    transient long cachedTimestamp;      // 재계산 가능한 값 — 저장 불필요
}

transient 필드는 직렬화 스트림에 포함되지 않습니다. 역직렬화 시에는 해당 타입의 기본값으로 초기화됩니다. String은 null, int는 0, boolean은 false입니다.

문제는 역직렬화 후에 transient 필드가 null인 상태로 객체가 반환된다는 점입니다. dbConnection을 쓰는 코드가 있다면 즉시 NPE가 발생합니다. 역직렬화 후 반드시 재초기화가 필요한 필드는 명시적으로 처리해야 합니다. 이 처리를 하는 곳이 커스텀 readObject()입니다.

✏️ 5. 커스텀 readObject / writeObject

기본 직렬화 동작을 덮어쓰고 싶을 때 이 두 메서드를 선언합니다. 접근 제어자가 private인 것이 포인트입니다. 인터페이스 메서드가 아니지만 ObjectOutputStream과 ObjectInputStream이 리플렉션으로 이 메서드를 찾아서 호출합니다.

public class UserSession implements Serializable {
    private static final long serialVersionUID = 1L;

    String userId;
    transient String sensitiveToken;

    private void writeObject(ObjectOutputStream out) throws IOException {
        out.defaultWriteObject();                         // 기본 직렬화 (transient 제외 필드)
        out.writeObject(encrypt(this.sensitiveToken));   // 암호화해서 별도 기록
    }

    private void readObject(ObjectInputStream in) throws IOException, ClassNotFoundException {
        in.defaultReadObject();                               // 기본 역직렬화
        this.sensitiveToken = decrypt((String) in.readObject()); // 복호화 후 복원
        // 여기서 transient 필드 재초기화도 가능합니다
    }
}

defaultWriteObject()와 defaultReadObject()를 호출하면 기본 동작은 그대로 유지하면서 추가 데이터를 앞뒤로 붙일 수 있습니다. 단, writeObject에서 추가로 쓴 데이터는 readObject에서 같은 순서로 읽어야 합니다. 스트림 포인터를 직접 다루는 것이기 때문에 순서가 어긋나면 엉뚱한 값이 읽힙니다.

readResolve()도 알아두면 좋습니다. 역직렬화 직후 반환할 객체를 바꾸고 싶을 때 씁니다. 싱글턴 패턴에서 역직렬화로 인스턴스가 여러 개 생기는 것을 막을 때 사용합니다.

public class DatabaseConfig implements Serializable {
    private static final DatabaseConfig INSTANCE = new DatabaseConfig();

    private Object readResolve() {
        return INSTANCE; // 역직렬화 결과를 항상 싱글턴 인스턴스로 교체
    }
}

☠️ 6. 역직렬화 취약점 — 가장 위험한 함정

Java 역직렬화는 실제로 심각한 보안 취약점의 원인이 된 역사가 있습니다. 원리를 이해해두는 것이 좋습니다.

ObjectInputStream.readObject()는 스트림에 적힌 클래스 이름을 보고 현재 ClassLoader에서 그 클래스를 찾아 인스턴스화합니다. 그리고 그 클래스에 readObject()가 있으면 실행합니다.

문제는 여기서 시작합니다. 공격자가 악의적으로 조작한 바이트 스트림을 서버에 보내면, 서버는 스트림에 적힌 클래스를 그대로 역직렬화합니다. 클래스패스에 있는 클래스라면 어떤 클래스든 로딩할 수 있습니다.

Apache Commons Collections 라이브러리를 예로 들면, 이 라이브러리의 특정 클래스들은 readObject() 내부에서 변환 체인(Transformer chain)을 실행합니다. 공격자는 이 클래스들을 연쇄적으로 조합해서 최종적으로 Runtime.exec()를 호출하는 바이트 스트림을 만들어낼 수 있습니다.

악의적 직렬화 스트림 전송
→ ObjectInputStream.readObject()
→ InvokerTransformer.readObject()   ← 클래스패스에 있는 정상 클래스
→ ChainedTransformer.transform()
→ Runtime.getRuntime().exec("...")  ← 원격 코드 실행

코드를 하나도 수정하지 않았는데, 신뢰할 수 없는 바이트 스트림을 받아서 역직렬화하는 것만으로 서버에서 임의 명령이 실행됩니다. 2015년에 공개된 이 취약점은 WebLogic, JBoss, Jenkins 등 광범위한 시스템에 영향을 미쳤습니다.

대응 방법은 크게 세 가지입니다.

첫째, 신뢰할 수 없는 소스의 데이터는 역직렬화하지 않습니다. 근본적인 해결책입니다. 외부에서 받은 데이터를 Java 직렬화 형식으로 받을 이유가 없다면, JSON이나 Protobuf를 쓰는 것이 맞습니다.

둘째, Java 9+의 ObjectInputFilter로 허용 클래스를 제한합니다.

ObjectInputStream ois = new ObjectInputStream(inputStream);

// 화이트리스트 방식: 허용할 클래스만 명시
ois.setObjectInputFilter(filterInfo -> {
    Class<?> cl = filterInfo.serialClass();
    if (cl == null) return ObjectInputFilter.Status.UNDECIDED;

    if (cl == Point.class || cl == User.class) {
        return ObjectInputFilter.Status.ALLOWED;
    }
    return ObjectInputFilter.Status.REJECTED; // 나머지는 전부 차단
});

셋째, 역직렬화 자체를 막는 래퍼를 씁니다. 레거시 시스템에서 어쩔 수 없이 ObjectInputStream을 써야 하지만 특정 클래스 이외의 역직렬화는 막고 싶을 때 사용하는 방어적 패턴입니다.

📉 7. Java 직렬화의 현재

Effective Java를 쓴 Joshua Bloch는 Java 직렬화 설계에 직접 참여했던 사람입니다. 3판에서 이렇게 말합니다.

"자바 직렬화는 위험 요소가 너무 많다. 신규 시스템을 설계할 때는 자바 직렬화를 쓸 이유가 거의 없다."

Java 팀도 이 판단에 동의합니다. Project Valhalla와 함께 논의되는 방향 중 하나는 Serializable을 사실상 deprecated 처리하는 것입니다.

현대적인 대안들과 비교하면 이렇습니다.

언어 간 호환JVM 전용모든 언어모든 언어

그렇다고 Serializable을 쓰는 것이 무조건 나쁜 선택은 아닙니다. JVM 기반 분산 캐시(예: Hazelcast), Java EE 레거시 시스템, HttpSession 직렬화처럼 JVM끼리 통신하는 구조에서는 여전히 합리적인 선택입니다. 다만 선택할 때 이 글에서 다룬 함정들을 의식하고 있어야 한다는 것입니다.

🤔 마무리

두 파트를 거치면서 Java 직렬화가 하는 일을 처음부터 끝까지 추적해 봤습니다.

직렬화 스트림에는 값뿐만 아니라 클래스 이름, 필드 이름, 타입 코드, serialVersionUID까지 전부 박혀 있고, 역직렬화는 이 정보를 읽어 ClassLoader에서 클래스를 찾고 생성자를 우회해서 객체를 만들어냅니다. 생성자가 실행되지 않기 때문에 유효성 검사 로직은 역직렬화 경로에서 무력화됩니다. serialVersionUID를 명시하지 않으면 메서드 하나 추가했을 뿐인데 기존 데이터를 읽지 못하게 되고, 신뢰할 수 없는 스트림을 역직렬화하면 원격 코드 실행까지 가능합니다.
