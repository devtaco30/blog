모든 복잡한 시스템은 단순하게 시작해야 합니다. 오버엔지니어링의 유혹을 이기고, 일단 동작하는 가장 단순한 구조를 만드는 것이 첫 번째 목표였습니다.

🏗️ 1. Phase 1 구조

전체 흐름

Phase 1은 단일 JAR로 모든 모듈이 같은 JVM에서 실행됩니다.

HTTP 요청
    │
    ▼
OrderApiService (api 모듈)
    │
    ├── AccountService      — 잔고·보유 검증
    ├── OrderCommandService — 주문 DB 저장
    └── (체결은 별도 REST API로 직접 호출)

주문을 접수하면 PENDING 상태로 DB에 저장됩니다. 체결은 외부에서 POST /orders/{orderId}/fill을 호출해야 발생합니다. 실제 거래소처럼 자동으로 매칭되지 않습니다.

이건 의도적인 결정이었습니다. 매칭 엔진을 붙이기 전에 도메인 모델을 먼저 검증하는 것이 목적이었습니다.

🔒 2. 매수 주문 구현하면서 만난 첫 번째 문제

처음에는 단순하게 생각했습니다

매수 주문 처리 흐름은 직관적으로 보였습니다.

1. 잔고 조회
2. 주문 금액과 비교
3. 충분하면 주문 접수

그런데 구현하다가 문제가 보이기 시작했습니다.

"동시에 두 요청이 들어오면 어떻게 되지?"

잔고: 100만원

스레드 A: 잔고 조회 → 100만원 확인 → (아직 접수 전)
스레드 B: 잔고 조회 → 100만원 확인 → (아직 접수 전)
                                          ↓
                    스레드 A: 70만원 주문 접수
                    스레드 B: 70만원 주문 접수
                                          ↓
                              140만원 주문 발생 (잔고 초과!)

둘 다 "잔고 충분하다"는 확인을 마친 뒤 각자 주문을 접수합니다. 이것이 TOCTOU(Time Of Check To Time Of Use) 문제입니다. 확인하는 시점과 사용하는 시점 사이에 상태가 바뀝니다.

문제의 본질은 이렇습니다. 잔고 확인과 주문 접수는 별개의 시점입니다. 아무리 꼼꼼하게 검증 로직을 짜도, 두 작업이 원자적으로 처리되지 않으면 경합이 발생합니다.

SELECT FOR UPDATE로 해결

확인과 접수 사이에 다른 트랜잭션이 끼어들지 못하도록 해야 합니다. DB의 SELECT FOR UPDATE가 그 역할을 합니다. Account 행에 배타적 락을 걸면, 이 락이 해제될 때까지 다른 트랜잭션은 같은 행에 접근할 수 없습니다.

@Transactional
public PlaceOrderResultView placeBuyOrder(BuyOrderCommand command, Account account,
        Supplier<BigDecimal> unpaidSumSupplier) {

    // SELECT ... FOR UPDATE — 락 획득, 다른 트랜잭션은 여기서 대기
    Account lockedAccount = accountService.getAccountByIdForUpdate(account.getId())
        .orElseThrow(() -> new IllegalArgumentException("Account not found"));

    // 락 획득 후에 미결제 미수금 조회
    // 락 전에 조회하면 TOCTOU 문제가 재발합니다
    BigDecimal pendingUnpaidSum = unpaidSumSupplier.get();

    // 출금 가능 금액 = 잔고 - 예약증거금 합계 - 미결제 미수금
    BigDecimal currentReservedMarginSum =
        orderRepository.sumReservedMarginByAccountId(lockedAccount.getAccountId());

    BigDecimal withdrawableBalance = lockedAccount.getBalance()
        .subtract(currentReservedMarginSum)
        .subtract(pendingUnpaidSum);

    if (orderAmount.compareTo(buyLimit) > 0) {
        throw new IllegalStateException("매수 가능 금액 초과");
    }
    // 주문 저장...
}

트랜잭션 A: Account 락 획득 → 잔고 확인 → 주문 접수 → 락 해제
트랜잭션 B:                   (여기서 대기)             → 락 획득 → 잔고 확인 → ...

→ B는 A가 끝난 후 실제 잔고를 보게 됩니다
→ 잔고 초과 주문이 구조적으로 차단됩니다

⚠️ 3. 락을 잡고 나서 만난 두 번째 문제

락 보유 중에 너무 많은 일을 하고 있었습니다

비관적 락으로 정합성 문제는 해결했습니다. 그런데 락을 잡은 채로 처리하는 코드를 보다가 문제를 발견했습니다.

초기 구현에서는 락을 잡은 채로 PENDING 주문들의 예약증거금을 애플리케이션에서 합산했습니다.

// 초기 구현: 락 보유 중 애플리케이션에서 합산
List<Order> pendingOrders = orderRepository.findPendingByAccountId(accountId);
BigDecimal reservedSum = pendingOrders.stream()
    .map(Order::getReservedMargin)
    .reduce(BigDecimal.ZERO, BigDecimal::add);

주문 목록을 가져오는 쿼리와 애플리케이션 합산이 모두 락을 쥔 채로 실행됩니다. 동시 요청이 많을수록 다른 트랜잭션들이 길게 대기하고, 커넥션 풀 고갈로 이어집니다.

비관적 락은 보유 시간이 짧을수록 좋습니다. 락을 잡고 있는 동안 다른 모든 요청이 대기합니다. 합산 연산을 DB에 넘기는 것만으로도 락 보유 시간을 크게 줄일 수 있습니다.

DB SUM 쿼리로 교체 (ADR-001)

// 개선: DB에서 한 번에 합산
BigDecimal currentReservedMarginSum =
    orderRepository.sumReservedMarginByAccountId(lockedAccount.getAccountId());

쿼리 한 번으로 끝납니다. 락 보유 시간이 단축됩니다.

🔑 4. 매도 주문 구현하면서 만난 데드락 위험

매도는 락이 하나 더 필요했습니다

매수 주문은 잔고(Account)만 확인하면 됩니다. 그런데 매도를 구현하면서 보유 수량(Holding)도 확인해야 한다는 걸 알게 됐습니다.

@Transactional
public PlaceOrderResultView placeSellOrder(SellOrderCommand command, Account account) {

    // Holding 행 락 — 보유 수량 확인
    Holding holding = accountService.getHoldingForUpdate(account.getId(), command.stockCode())
        .orElseThrow(() -> new IllegalStateException("보유 종목이 아님: " + command.stockCode()));

    if (holding.getQuantity() < command.quantity()) {
        throw new IllegalStateException("매도 수량 초과");
    }
    // 주문 저장...
}

매수는 Account 락, 매도는 Holding 락. 지금은 각각 하나씩이라 괜찮습니다.

그런데 여기서 한 가지를 더 생각하게 됐습니다.

"나중에 Account와 Holding 두 락이 동시에 필요한 경로가 생기면 어떻게 될까?"

락 순서가 다르면 데드락이 됩니다

트랜잭션 A: Account 락 → (Holding 락 필요) → 대기 중
트랜잭션 B: Holding 락 → (Account 락 필요) → 대기 중

→ A는 B가 쥔 Holding 락을 기다리고
→ B는 A가 쥔 Account 락을 기다립니다
→ 영원히 대기 (데드락)

지금 당장은 문제가 없더라도, 두 락이 필요한 경로가 하나라도 생기면 언제 터질지 모르는 시한폭탄이 됩니다.

락 획득 순서 통일 (ADR-003)

모든 코드 경로에서 반드시 Account → Holding 순서로만 락을 획득합니다.

Account 락 먼저 → Holding 락 나중 (이 순서만 허용)

이 규칙을 지키면 순환 대기 자체가 불가능합니다. A와 B 모두 Account 락을 먼저 시도하므로, 둘 중 하나가 Account 락을 쥐면 나머지는 거기서 대기합니다. Holding 락을 먼저 쥔 상태에서 Account 락을 기다리는 상황이 구조적으로 없어집니다.

단순한 규칙이지만 코드 어딘가에 명시해두지 않으면, 나중에 누군가 순서를 모르고 뒤집을 수 있습니다. ADR-003으로 이 결정을 기록해둔 이유입니다.

📐 5. @Transactional 원칙

Phase 1을 진행하면서 @Transactional을 다루는 원칙도 정리하게 됐습니다.

클래스 레벨 선언 금지

// 금지: 모든 메서드에 쓰기 트랜잭션이 걸립니다
@Transactional
public class OrderCommandService { ... }

// 필수: 필요한 메서드에만 명시합니다
public class OrderCommandService {

    @Transactional
    public PlaceOrderResultView placeBuyOrder(...) { ... }

    @Transactional(readOnly = true)
    public Order getOrder(Long orderId) { ... }
}

클래스 레벨에 걸면 읽기 전용 메서드도 쓰기 트랜잭션으로 실행됩니다. 불필요한 락과 스냅샷 생성 비용이 발생합니다.

트랜잭션 붙이는 기준

상황어노테이션
DB 상태 변경 (save, update, delete)@Transactional
두 개 이상의 쿼리를 같은 스냅샷으로 읽어야 할 때@Transactional(readOnly = true)
Lazy Loading 접근이 있는 경우@Transactional(readOnly = true)
단일 Repository 메서드 하나만 호출생략 (JPA가 자체 트랜잭션 처리)

🪲 6. Lazy Loading 함정

매칭 엔진을 붙이면서 만난 버그

Phase 1 도메인 모델이 안정된 뒤, 매칭 엔진을 붙이기 시작했습니다. DB에서 PENDING 주문을 조회해 오더북에 로드하는 코드를 작성하면서 예상치 못한 예외가 터졌습니다.

// OrderQueryService — @Transactional 없음
public List<Order> getPendingByStockCodeSortedByTime(String stockCode) {
    return orderRepository.findByStatusAndStockCode(...);
    // 메서드가 반환될 때 JPA 세션이 닫힙니다
}

// MatchingConsumer — 세션 밖에서 Lazy 필드 접근
private static OrderEntry toEntry(Order order) {
    return new OrderEntry(
        order.getOrderId(),
        order.getAccount().getAccountId(), // ← LazyInitializationException!
        ...
    );
}

JPA는 @ManyToOne(fetch = FetchType.LAZY) 관계를 처음 접근하는 시점에 DB에서 조회합니다. 이때 JPA 세션이 열려 있어야 합니다. 그런데 getPendingByStockCodeSortedByTime()이 반환되는 순간 세션이 닫힙니다. 이후 order.getAccount()에 접근하면 세션이 없어 예외가 터집니다.

getPendingByStockCodeSortedByTime() 반환
    → JPA 세션 닫힘
        → order.getAccount() 접근
            → 세션 없음 → LazyInitializationException

해결 방법 두 가지

방법 A: JOIN FETCH

@Query("SELECT o FROM Order o JOIN FETCH o.account WHERE ...")
List<Order> findPendingByStockCodeWithAccount(...);

쿼리 시점에 account를 함께 로드합니다. 세션이 닫힌 후에도 접근 가능합니다.

방법 B: accountId 직접 보유 (ADR-005 채택)

@Column(name = "account_id", insertable = false, updatable = false)
private Long accountId;  // FK 컬럼을 읽기 전용으로 직접 매핑

@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "account_id", nullable = false)
private Account account;

toEntry()에서 실제로 필요한 건 accountId 하나입니다. Account 객체 전체를 JOIN FETCH해서 올리는 건 과잉입니다. Order가 Account Aggregate를 ID로만 참조하는 형태는 DDD의 Aggregate 경계 원칙과도 맞고, Lazy Loading 의존 자체가 사라집니다.

🤔 7. Phase 1의 한계

단순한 구조 덕분에 도메인 모델을 빠르게 검증할 수 있었습니다. 하지만 한계도 명확했습니다.

  1. 체결이 없습니다: 주문은 쌓이는데 자동으로 매칭되지 않습니다
  2. API 스레드가 매칭까지 담당해야 합니다: 매칭 로직을 붙이면 HTTP 스레드가 블로킹됩니다
  3. 스케일 아웃 불가: 오더북이 인메모리에 있으면 서버를 두 대로 늘릴 수 없습니다
