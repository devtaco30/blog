[Java Deep Dive] Serializable 깊이 파기 — Part 1: 객체가 바이트가 되는 과정

Python이나 JavaScript와 달리 Java는 왜 Serializable을 선언해야 하는지, 메서드가 하나도 없는 이 인터페이스가 무슨 일을 하는지 묻는 글입니다. | ObjectOutputStream이 만든 실제 바이트를 열어 보고, 참조 객체가 들어 있을 때는 어떻게 되는지 확인합니다.

안녕하세요. 이번 포스팅에서는 Java의 Serializable을 바이트 스트림 수준까지 직접 뜯어보려 합니다.

5년 넘게 Java를 쓰면서 implements Serializable을 수도 없이 작성했지만, 사실 "왜 이게 필요한가"를 제대로 생각해본 적이 없었습니다. Python이나 JavaScript에서는 json.dumps(), JSON.stringify() 한 줄로 끝나는데 Java는 왜 인터페이스까지 만들어서 명시적으로 선언해야 할까요? 그리고 이 인터페이스는 메서드가 하나도 없는데, 대체 무슨 역할을 하는 걸까요?

이 궁금증에서 시작해서 ObjectOutputStream이 실제로 어떤 바이트를 만들어내는지까지 추적해 보겠습니다.

🌍 1. Python도 JS도 있는데, 왜 Java만 선언이 필요한가

Python에도 pickle, JavaScript에도 JSON.stringify가 있습니다. 하지만 이 둘은 "직렬화"라는 단어를 쓰면서도 Java의 Serializable과 결이 다릅니다.

Python의 pickle을 먼저 보겠습니다.

import pickle

class User:
    def __init__(self, name, age):
        self.name = name
        self.age = age

user = User("Kim", 30)
data = pickle.dumps(user)  # 아무 선언 없이 그냥 됩니다

아무런 사전 선언 없이 직렬화됩니다. 왜 그럴까요? Python 객체는 내부적으로 __dict__라는 딕셔너리를 들고 있습니다. user.__dict__를 찍어보면 {'name': 'Kim', 'age': 30}이 나옵니다. 객체가 이미 "직렬화 가능한 구조"로 존재하는 셈입니다. pickle은 이 딕셔너리를 그냥 저장하면 됩니다.

JavaScript도 비슷합니다.

const user = { name: "Kim", age: 30 };
JSON.stringify(user); // '{"name":"Kim","age":30}'

JavaScript 객체는 런타임에 프로퍼티가 자유롭게 추가되고, 구조 자체가 JSON과 거의 동일합니다. 타입 정보를 별도로 기록할 필요가 없습니다.

Java는 사정이 다릅니다.

User user = new User("Kim", 30);
// 이걸 어떻게 바이트로 만들 것인가?

Java 객체는 JVM 힙 위에 있습니다. 필드는 강한 타입으로 선언되어 있고, 클래스 계층 구조가 있으며, 참조 관계가 복잡하게 얽혀 있을 수 있습니다. 이 객체를 바이트로 만들려면 단순히 "값"만 저장해서는 부족합니다. 나중에 이 바이트를 받은 쪽이 어떤 클래스의 어떤 필드인지를 알아야 객체를 복원할 수 있기 때문입니다.

게다가 Java가 Serializable을 설계한 1997년, 주된 목적은 **RMI(Remote Method Invocation)**였습니다. 네트워크 너머에 있는 JVM에 객체를 그대로 전송해서 원격 메서드를 호출하는 기술입니다. 단순한 데이터 전송이 아니라, 클래스 정보를 포함한 완전한 객체 상태를 전달해야 했습니다.

그래서 Java는 "이 클래스는 직렬화 가능하다"는 것을 개발자가 명시적으로 선언하도록 설계했습니다.

🏷️ 2. 메서드가 하나도 없는 인터페이스가 하는 일

Serializable의 소스를 처음 열어봤을 때 당황했습니다.

// java.io.Serializable
public interface Serializable {
    // 아무것도 없습니다
}

메서드도 없고, 상수도 없습니다. 이런 인터페이스를 **마커 인터페이스(Marker Interface)**라고 합니다. 구현을 강제하는 게 아니라, "이 클래스는 특정 속성을 갖는다"는 타입 정보를 JVM에게 알려주는 역할을 합니다.

ObjectOutputStream은 writeObject()를 호출할 때 이렇게 확인합니다.

// ObjectOutputStream 내부 (단순화)
private void writeObject0(Object obj) throws IOException {
    Class<?> cl = obj.getClass();

    // Serializable을 구현하지 않으면 예외
    if (!(obj instanceof Serializable)) {
        throw new NotSerializableException(cl.getName());
    }
    // ...
}

instanceof 체크로 마커 인터페이스를 확인하는 것입니다. 선언 하나가 JVM에게 "이 객체는 바이트 스트림으로 변환해도 된다"는 허가증이 됩니다.

🔧 3. ObjectOutputStream은 실제로 무슨 일을 하는가

직렬화는 ObjectOutputStream.writeObject()에서 시작됩니다. 이 메서드가 객체를 받아서 바이트 스트림을 만드는 과정을 따라가 보겠습니다.

ByteArrayOutputStream baos = new ByteArrayOutputStream();
ObjectOutputStream oos = new ObjectOutputStream(baos);
oos.writeObject(new User("Kim", 30));
byte[] bytes = baos.toByteArray();

내부적으로는 크게 세 단계로 동작합니다.

첫째, 클래스 메타데이터를 수집합니다.

ObjectStreamClass가 이 역할을 합니다. 리플렉션으로 클래스를 분석해서 직렬화 가능한 필드 목록을 만듭니다. transient나 static으로 선언된 필드는 제외됩니다.

// ObjectStreamClass 내부 (단순화)
ObjectStreamClass desc = ObjectStreamClass.lookup(User.class);
ObjectStreamField[] fields = desc.getFields();
// → [age(int), name(String)]  (알파벳 순으로 정렬됩니다)

필드가 알파벳 순으로 정렬된다는 점이 처음에는 의외였습니다. 클래스에 선언한 순서가 아닙니다.

둘째, serialVersionUID를 결정합니다.

클래스에 serialVersionUID를 직접 선언하지 않았다면, JVM이 클래스 구조를 기반으로 자동 계산합니다. 클래스 이름, 인터페이스 목록, 필드 이름과 타입, 메서드 시그니처를 SHA-1 해시로 계산한 값입니다. 이 값은 역직렬화 시 클래스 버전 호환성 체크에 쓰입니다. (이 이야기는 Part 2에서 자세히 다루겠습니다.)

셋째, 스트림에 씁니다.

클래스 메타데이터를 먼저 기록하고, 그 뒤에 실제 필드 값을 씁니다. 이 순서가 바이트 스트림을 읽을 때 "어떤 클래스인지 먼저 파악하고, 그 다음 값을 복원"하는 것을 가능하게 합니다.

🔬 4. 실제 바이트를 직접 뜯어보자

이제 실제로 바이트를 만들어서 hex로 읽어보겠습니다. 최대한 단순한 클래스를 사용합니다.

import java.io.Serializable;

public class Point implements Serializable {
    int x;
    int y;

    public Point(int x, int y) {
        this.x = x;
        this.y = y;
    }
}

new Point(1, 2)를 직렬화하면 다음 바이트가 나옵니다.

눈에 띄는 점이 있습니다. 원본 데이터인 x=1, y=2는 맨 마지막 8바이트에 불과합니다. 나머지 30여 바이트는 전부 클래스 메타데이터입니다. 클래스 이름, 필드 이름, 타입 코드, serialVersionUID까지 모두 스트림에 포함됩니다. 이것이 Java 직렬화가 Python pickle이나 JSON보다 크기가 큰 이유이기도 합니다.

이제 String 필드가 포함된 경우를 보겠습니다.

public class User implements Serializable {
    String name;  // Object 타입
    int age;
}

new User("Kim", 30)을 직렬화하면 필드 선언 부분이 달라집니다.

🔗 5. 참조 객체가 포함되면 어떻게 되는가

직렬화가 흥미로워지는 지점은 객체 안에 또 다른 객체가 있을 때입니다.

public class Order implements Serializable {
    String orderId;
    User user;      // User도 Serializable을 구현해야 합니다
    int amount;
}

ObjectOutputStream은 Order를 직렬화하면서 user 필드를 만나면 재귀적으로 User 객체도 직렬화합니다. 이때 같은 객체를 두 번 직렬화하지 않기 위해 핸들 테이블을 관리합니다.

Order order = new Order();
order.user = user;

Order order2 = new Order();
order2.user = user; // 같은 user 객체 참조

이 두 Order를 같은 스트림에 쓰면, user는 한 번만 직렬화되고 두 번째 참조는 TC_REFERENCE (0x71)와 핸들 번호로 대체됩니다. 덕분에 순환 참조도 스택 오버플로우 없이 처리할 수 있고, 역직렬화 시 같은 객체 참조 관계도 복원됩니다.

🤔 마무리 — 그래서 어디에 써야 하는가

Java 직렬화가 만들어내는 바이트 스트림을 보면, 설계 의도가 명확합니다. 단순한 데이터 전송이 아니라 JVM 객체 그래프의 완전한 스냅샷을 만드는 것입니다. 클래스 메타데이터, 타입 정보, 객체 참조 관계까지 모두 포함합니다.

그래서 Java 직렬화는 같은 JVM끼리 객체를 주고받을 때 (RMI, EJB, Java 기반 캐시) 강력하지만, 그 외의 용도에서는 다소 무겁습니다. JSON이나 Protocol Buffers가 언어 간 통신에 선호되는 이유이기도 합니다.

다음 파트에서는 이 바이트 스트림을 받아서 다시 객체로 복원하는 과정, 그리고 serialVersionUID가 왜 존재하고 어떻게 클래스 버전 불일치를 만들어내는지를 다루겠습니다.
