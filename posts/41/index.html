안녕하세요. Java/Kotlin 백엔드 개발자로서 G1GC(Garbage-First Garbage Collector)를 완벽하게 이해하는 것은 대규모 애플리케이션의 성능 최적화에 필수적입니다.

본 포스팅(1부)에서는 G1GC의 기본 개념과 핵심 원리를 다룹니다. Region 구조, Freelist, RSet, CSet, SATB, TAMS, tri-color marking, Root Set, STW 등 핵심 개념들을 심층적으로 설명합니다.

2부에서는 실제 동작 과정(Young GC, Mixed GC, Full GC)과 실무 활용 방법을 다룹니다.

🎯 1. G1GC가 뭔가요?

기존 GC의 문제점

기존 GC (Serial, Parallel GC)는 이렇게 동작했습니다:

전체 힙을 한 번에 수집
  ↓
STW 시간이 길어짐 (수백 ms ~ 수초)
  ↓
애플리케이션이 멈춤
  ↓
사용자 경험 저하

예시:

  • 힙이 8GB면 전체를 스캔해야 함
  • 살아있는 객체가 많으면 STW가 길어짐
  • 큰 힙에서는 예측 불가능한 지연 발생

기존 GC vs G1GC

기존 GC (Serial, Parallel GC):

힙 구조:
  Young Generation (연속된 메모리)
  Old Generation (연속된 메모리)
  
수집 방식:
  전체 세대를 한 번에 수집
  → STW 시간이 길어짐 (수백 ms ~ 수초)

G1GC:

힙 구조:
  Region 0, Region 1, Region 2, ... (작은 조각들)
  각 Region은 Eden/Survivor/Old 역할
  
수집 방식:
  쓰레기 많은 Region부터 선택적으로 수집
  → STW 시간이 짧음 (수십 ms)

비유:

  • 기존 GC: 집 전체를 한 번에 청소 (오래 걸림)
  • G1GC: 방별로 나눠서, 쓰레기 많은 방부터 청소 (빠름)

왜 Region으로 나누나요?

Region으로 나누면:

1. 작은 단위로 수집
   → 빠른 수집 가능
   
2. 우선순위 정하기 쉬움
   → 쓰레기 많은 Region부터
   
3. 예측 가능한 STW
   → Region 크기만큼만 STW
   
4. 확장성
   → 힙이 커져도 Region 단위로 처리

예시:

힙 크기: 8GB
Region 크기: 2MB
Region 개수: 약 4000개

기존 GC:
  전체 8GB 수집 → STW 수백 ms ~ 수초
  
G1GC:
  Region 10개만 수집 (20MB) → STW 수십 ms
  쓰레기 많은 Region부터 우선 수집

🏗️ 2. Region이 뭔가요?

Region = 힙을 나눈 작은 조각

⚠️ Region은 G1GC의 핵심입니다!

힙을 작은 조각으로 나눕니다:

전체 힙 (예: 8GB)
  ↓
Region으로 분할 (각 Region: 2MB)
  ↓
Region 0, Region 1, Region 2, ... Region 4000개

기존 GC와의 차이:

기존 GC (Serial, Parallel):
  힙 = Young Generation (연속) + Old Generation (연속)
  → 세대별로 연속된 메모리 공간
  
G1GC:
  힙 = Region 0 + Region 1 + Region 2 + ...
  → 작은 조각들로 나눔
  → 각 Region이 Eden/Survivor/Old 역할 가능

⚠️ 핵심: Eden, Survivor, Old는 Region의 '상태'입니다!

Region은 물리적인 메모리 조각이고, Eden/Survivor/Old는 그 Region의 현재 역할(상태)입니다.

┌─────────────────────────────────────┐
│  Region의 상태 (역할)                 │
├─────────────────────────────────────┤
│  1. Eden 상태                       │
│     → 새로 만든 객체가 들어감        │
│     (예: new A(), new B())          │
│                                     │
│  2. Survivor 상태                   │
│     → GC에서 살아남은 객체가 이동    │
│                                     │
│  3. Old 상태                        │
│     → 오래 살아남은 객체가 이동      │
│                                     │
│  4. Humongous 상태                  │
│     → 엄청 큰 객체 (Region 크기의    │
│        50% 이상)                     │
│                                     │
│  5. Free 상태                       │
│     → 빈 Region (Freelist에 있음)    │
└─────────────────────────────────────┘

⚠️ 중요한 점: Region의 상태는 계속 바뀝니다!

Region의 생명주기:

1. Free 상태 (빈 Region)
   ↓
2. Eden 상태로 변경 (새 객체 할당)
   ↓
3. GC 발생 → 살아있는 객체는 Survivor로 이동
   ↓
4. 빈 Region이 됨 (Free 상태)
   ↓
5. 다시 Eden 상태로 사용
   ↓
6. 여러 번 GC에서 살아남으면 Old 상태로 변경
   ↓
7. Old Region 수집 → 다시 Free 상태
   ↓
8. 다시 Eden 상태로 사용 가능

비유:

  • Region = 방
  • Eden/Survivor/Old = 방의 용도 (거실, 침실, 서재)
  • 방의 용도는 필요에 따라 바뀜!

실제 예시:

시작:
  Region 0: Free 상태
  
객체 할당:
  Region 0: Eden 상태 (A 객체 할당)
  Region 1: Eden 상태 (B 객체 할당)
  
GC 발생:
  A 객체 살아있음 → Region 2 (Survivor 상태)로 이동
  B 객체 가비지 → 수집
  Region 0: Free 상태 (다시 사용 가능)
  Region 1: Free 상태
  
다시 객체 할당:
  Region 0: Eden 상태 (C 객체 할당)
  
여러 번 GC에서 살아남:
  Region 2: Old 상태로 변경

기존 GC와의 차이:

기존 GC:
  Eden 영역 = 고정된 메모리 공간
  Old 영역 = 고정된 메모리 공간
  → 물리적으로 분리됨
  
G1GC:
  Eden Region = 현재 Eden 상태인 Region들
  Old Region = 현재 Old 상태인 Region들
  → 물리적으로 분리되지 않음
  → Region의 상태만 다름

⚠️ Region이 흩어져 있는데 찾는 게 느리지 않나요?

걱정하지 마세요! G1GC는 Region들을 상태별로 연결 리스트로 관리합니다.

핵심: 탐색이 아니라 리스트 순회입니다!

물리적: Region들이 메모리에 흩어져 있음
논리적: 상태별 연결 리스트로 관리
  - Eden Region 리스트
  - Survivor Region 리스트  
  - Old Region 리스트
  - Freelist (Free Region 리스트)

GC 시: 리스트를 순회하면서 처리 (빠름)

왜 Region으로 나눌까요?

  1. 빠른 수집: 작은 Region만 수집하면 빠름
  2. 예측 가능: Region 크기만큼만 STW 발생
  3. 우선순위: 쓰레기 많은 Region부터 수집 (Garbage-First!)
  4. 확장성: 힙이 커져도 Region 단위로 처리

🔑 3. 핵심 개념들 이해하기

3-1. Freelist (빈 Region 목록)

Freelist는 "사용 가능한 빈 Region들의 연결 리스트"입니다.

비유:

  • 아파트의 빈 방 목록
  • 새 입주자가 오면 목록에서 방 배정

동작:

1. 새 객체 생성
   ↓
2. Freelist에서 빈 Region 찾기
   ↓
3. Region을 Eden 상태로 변경하고 객체 할당
   ↓
4. GC 후 Region이 비면 Freelist에 다시 추가

예시:

A a = new A();  // Freelist에서 Region 가져와서 할당
B b = new B();  // 또 다른 Region에서 할당

3-2. RSet (Remembered Set) - 가장 중요!

⚠️ RSet은 "다른 Region에서 나를 참조하는 객체를 기억하는 메모장"입니다!

왜 필요한가요?

문제 상황:

Region A (Old)에 객체 A가 있음
  ↓
객체 A가 Region B (Eden)의 객체 B를 참조함
  ↓
Region B만 GC하면?
  → 객체 B는 가비지인가요? 살아있나요?

답: 살아있어요! Region A의 객체 A가 참조하고 있으니까요.

하지만 문제:

  • Region B만 스캔하면 Region A의 참조를 모름
  • 객체 B를 잘못 수집할 수 있음

해결책: RSet

Region B의 RSet:
  "Region A의 객체 A가 나를 참조하고 있어요!"
  
Region B GC 시:
  1. Region B 내부 객체 확인
  2. RSet 확인 → Region A의 객체 A가 참조 중
  3. 객체 B는 살아있음으로 판단

비유:

  • RSet = "누가 나를 좋아하는지 기록한 메모장"
  • GC 시 이 메모장을 확인해서 잘못 수집하지 않음

실제 예시:

// Region A (Old)에 저장됨
static A a = new A();

// main 메서드에서
A localA = a;  // Region A의 객체를 참조

// Region A만 GC하면?
// → Stack의 localA가 참조하고 있으니 살아있음
// → RSet에 이 정보가 기록됨

3-3. CSet (Collection Set)

CSet은 "이번에 수집할 Region 목록"입니다.

비유:

  • 오늘 청소할 방 목록
  • 쓰레기 많은 방부터 우선순위 정함

선택 기준:

1. 쓰레기(가비지) 비율이 높은 Region
2. STW 시간 내에 수집 가능한 Region
3. 살아있는 객체가 적은 Region (복사 비용 적음)

예시:

Region 0: 가비지 80% → CSet에 포함
Region 1: 가비지 20% → CSet에 제외 (나중에)
Region 2: 가비지 90% → CSet에 포함 (우선순위 높음)

3-4. SATB (Snapshot-At-The-Beginning)

⚠️ SATB는 "Marking 시작할 때의 상태를 사진으로 찍어두는 것"입니다!

왜 필요한가요?

문제 상황:

Marking 시작:
  A → B → C (모두 살아있음)
  
Marking 중 (애플리케이션도 실행 중):
  A → B 참조 제거 (애플리케이션이 변경)
  B는 이제 가비지가 되어야 함
  
하지만 이미 B를 마킹했음
→ B를 수집하지 않음
→ Floating Garbage (일시적 가비지)

⚠️ SATB의 트레이드오프:

SATB는 안전성을 위해 정확성을 포기합니다:

1. Marking 시작 시점 스냅샷 찍기
   "이 시점에 A → B → C 모두 살아있어요"
   
2. Marking 중 참조 변경 발생
   → 변경 전 상태를 SATB Queue에 기록
   
3. Marking 완료 후
   → 스냅샷 시점에 살아있던 객체는 모두 마킹
   → 실제로는 가비지가 된 객체도 살려둠
   → Floating Garbage 발생

⚠️ 왜 공간 낭비를 허용하나요?

핵심: 두 가지 선택지가 있습니다:

선택 1: SATB (현재 방식) - 안전성 우선

Floating Garbage 허용
  → 일시적 메모리 낭비 (비치명적)
  → 다음 GC에서 수집됨
  → 프로그램 안정성 보장

선택 2: 정확하게 수집하려면?

살아있는 객체를 잘못 수집
  → 프로그램 크래시 💥 (치명적)
  → 데이터 손실
  → 서비스 중단

비유:

  • SATB: "의심스러운 물건은 일단 보관" (안전)
  • 정확하게 수집: "의심스러운 물건도 버림" (위험)

왜 이렇게 하나요?

1. 치명적 오류 vs 일시적 낭비:

살아있는 객체 수집 → 프로그램 크래시 💥
  vs
Floating Garbage → 메모리 일시적 낭비 (다음 GC에서 수집)

2. 다음 GC에서 수집됨:

이번 GC:
  B는 Floating Garbage로 남음 (일시적)
  
다음 GC:
  B는 마킹되지 않음
  → 정상적으로 수집됨

3. 실제로는 큰 문제 아님:

  • Floating Garbage는 보통 전체 힙의 작은 비율
  • 다음 GC에서 바로 수집됨
  • 메모리 부족 문제는 거의 발생하지 않음

비유:

  • 사진 찍을 때: "찍는 순간의 모습을 기록"
  • 나중에 변경되어도: "사진 속 모습은 그대로"
  • 일부는 이미 버려진 물건이지만, 안전하게 보관
  • 다음 정리 때 버리면 됨

실제 동작:

// Marking 시작 시점
A a = new A();
B b = new B();
a.ref = b;  // A가 B 참조

// Marking 중
a.ref = null;  // 참조 제거
// → 이전 참조(a.ref = b)를 SATB Queue에 기록

// Marking 완료 후
// → SATB Queue 처리: B는 살아있음으로 마킹
// → 하지만 실제로는 B는 가비지 (Floating Garbage)
// → 다음 GC에서 수집됨

⚠️ 중요한 점:

  • Floating Garbage는 정상적인 현상입니다
  • 안전성을 위한 트레이드오프입니다
  • 다음 GC에서 수집되므로 문제 없습니다

3-5. TAMS (Top-At-Mark-Start)

⚠️ TAMS는 "Marking 시작할 때의 Region 메모리 위치(포인터)를 기록하는 것"입니다!

핵심:

  • 시간이 아니라 메모리 주소를 기록합니다!
  • 객체 자체에 시간이 기록되는 게 아니라, Region의 TAMS 포인터와 객체의 메모리 주소를 비교합니다.

왜 필요한가요?

문제:

  • Marking 중에도 새 객체가 계속 생성됨
  • 새 객체는 자동으로 살아있음 (방금 만들었으니까)
  • 새 객체를 일일이 마킹할 필요 없음

해결책: TAMS

⚠️ Region 내부는 연속된 메모리 공간입니다!

Region 내부 메모리 구조:

Region (연속된 메모리 공간, 예: 2MB)
┌─────────────────────────────────────┐
│  [기존 객체들]                        │
│  주소: 0x1000 → 0x1500 → 0x2000    │
│  (오름차순, 낮은 주소부터 할당)       │
│  ← TAMS = 0x2000 (Marking 시작 시점) │
│  [Marking 중 새로 만든 객체들]        │
│  주소: 0x2000 → 0x2500 → 0x3000    │
│  (오름차순, 계속 증가)                │
│  ← Top = 0x3000 (현재 할당 위치)      │
└─────────────────────────────────────┘

메모리 주소: 오름차순 (낮은 주소 → 높은 주소)
할당 순서: 먼저 할당된 객체가 낮은 주소

⚠️ 핵심:

  • Region 내부는 연속된 메모리 공간
  • 메모리 주소는 오름차순 (낮은 주소 → 높은 주소)
  • 새 객체 할당 시 Top 포인터가 증가 (주소가 커짐)
  • TAMS는 특정 주소 위치를 기록

비교 방식:

객체 주소 < TAMS → Marking 대상 (기존 객체)
객체 주소 >= TAMS → 자동 살아있음 (새 객체)

왜 이렇게 동작하나요?

1. Region은 연속된 메모리 공간
2. 객체 할당 시 낮은 주소부터 순차적으로 할당
3. Top 포인터가 증가하면서 주소가 커짐
4. TAMS는 Marking 시작 시점의 Top 위치 기록
5. 이후 할당된 객체는 주소가 TAMS보다 큼

⚠️ 중요한 점:

  1. TAMS는 메모리 주소(포인터)입니다

    • 시간이 아니라 메모리 위치를 기록
    • Region 내부의 할당 위치를 가리키는 포인터

  2. 객체에 시간이 기록되지 않습니다

    • 객체 자체에는 시간 정보 없음
    • 객체의 메모리 주소와 TAMS 포인터를 비교

  3. 비교 방식:

    객체 주소 < TAMS → Marking 대상 (기존 객체)
객체 주소 >= TAMS → 자동 살아있음 (새 객체)

비유:

  • 책상 정리 시작 시점에 위치에 선 긋기 (시간이 아니라 위치)
  • 그 선 이후에 올려둔 물건은 "최근 것"이라 자동으로 살아있음
  • 물건 자체에 시간이 기록되는 게 아니라, 위치로 판단

예시:

// Marking 시작 (TAMS = 현재 Top 위치 기록)
// 예: TAMS = 0x2000

A a = new A();  
// 객체 주소: 0x1000
// 0x1000 < 0x2000 (TAMS 이전)
// → Marking 대상 (기존 객체)

// Marking 중
B b = new B();  
// 객체 주소: 0x2500
// 0x2500 >= 0x2000 (TAMS 이후)
// → 자동으로 살아있음 (마킹 불필요, 새 객체)

⚠️ TAMS는 모든 Region 타입에 적용됩니다:

  • Eden Region: 새 객체 할당 시 TAMS 이후
  • Survivor Region: 객체 복사 시 TAMS 이후
  • Old Region: 객체 승격 시 TAMS 이후

핵심 정리:

  • TAMS = 메모리 주소(포인터), 시간 아님
  • 객체 주소와 TAMS 비교로 새/기존 객체 구분
  • TAMS 이후 객체 = 자동 살아있음 (마킹 불필요)

3-6. Tri-Color Marking (3색 마킹)

⚠️ 마킹은 "살아있는 객체를 표시하는 것"입니다! (살리는 마킹)

⚠️ 핵심: 마킹된 객체는 모두 살아있습니다!

마킹의 의미:

  • 마킹된 객체 (Gray, Black) = 살아있음 = 수집 안됨
  • 마킹되지 않은 객체 (White) = 가비지 = 수집 대상

Tri-Color Marking은 객체를 3가지 색으로 구분합니다:

┌─────────────────────────────────────┐
│  White (흰색)                        │
│  → 아직 확인 안함                    │
│  → 가비지 후보 (마킹 안됨)            │
│  → 수집됨                            │
│                                     │
│  Gray (회색)                         │
│  → 확인했는데 자식은 아직 안봄       │
│  → 처리 대기 중 (마킹 중)            │
│  → 살아있음, 수집 안됨               │
│                                     │
│  Black (검은색)                     │
│  → 확인했고 자식도 다 확인함          │
│  → 살아있음 확정 (마킹 완료)          │
│  → 살아있음, 수집 안됨               │
└─────────────────────────────────────┘

⚠️ 중요한 점:

  1. Gray와 Black은 모두 살아있습니다

    • Gray: 마킹 중이지만 살아있음 (수집 안됨)
    • Black: 마킹 완료, 살아있음 확정 (수집 안됨)

  2. White만 수집됩니다

    • White: 마킹 안됨, 가비지 (수집됨)

  3. 마킹 = 살아있음 보장

    • 마킹된 객체는 절대 수집되지 않음
    • 안전성 보장

Marking 과정 (살아있는 객체 찾기):

⚠️ Root Set이 뭔가요?

Root Set은 "GC의 시작점이 되는 참조들의 집합"입니다!

Root Set의 구성:

┌─────────────────────────────────────┐
│  Root Set (GC의 시작점)               │
├─────────────────────────────────────┤
│  1. Stack의 지역 변수                │
│     예: main 메서드의 A a = new A() │
│                                     │
│  2. Static 변수                     │
│     예: A.STR = "ABC"               │
│                                     │
│  3. JNI 참조                        │
│     네이티브 코드에서 참조하는 객체   │
│                                     │
│  4. 활성 스레드                     │
│     실행 중인 스레드가 참조하는 객체 │
└─────────────────────────────────────┘

왜 Root Set이 필요한가요?

⚠️ 핵심: Root Set에서 도달 가능한 객체 = 살아있는 객체

Root Set
  ↓
객체 A (도달 가능, 살아있음)
  ↓
객체 B (도달 가능, 살아있음)
  ↓
객체 C (도달 가능, 살아있음)

객체 D (도달 불가능, 가비지) ← 수집됨
객체 E (도달 불가능, 가비지) ← 수집됨

⚠️ 중요한 점:

  1. Root Set에서 도달 가능 = 마킹됨 = 살아있음 = 수집 안됨
  2. Root Set에서 도달 불가능 = 마킹 안됨 = 가비지 = 수집됨

비유:

  • Root Set = 책장 정리의 시작점
  • 시작점에서 연결된 책 = 살아있는 책 (마킹됨, 수집 안됨)
  • 연결 안 된 책 = 버릴 책 (마킹 안됨, 수집됨)

⚠️ 혼동하기 쉬운 부분:

❌ 잘못된 이해:
  "참조가 안되면 수집 안됨"
  
✅ 올바른 이해:
  "참조가 안되면 가비지 = 수집됨"
  "참조가 되면 살아있음 = 수집 안됨"

Marking 과정:

1. 시작: 모든 객체 = White (마킹 안됨)

2. Root Set 확인:
   Root Set에서 참조하는 객체들 = Gray (마킹 시작, 살아있음)

3. 반복:
   - Gray 객체 하나 선택
   - 자식 객체들 확인
     * White → Gray로 변경 (마킹, 살아있음)
   - 현재 객체 = Black (마킹 완료, 살아있음 확정)

4. 완료:
   - White = 가비지 (Root Set에서 도달 불가능, 마킹 안됨, 수집됨)
   - Gray, Black = 살아있음 (Root Set에서 도달 가능, 마킹됨, 수집 안됨)

⚠️ 핵심 정리:

Root Set에서 도달 가능
  → 마킹됨 (Gray 또는 Black)
  → 살아있음
  → 수집 안됨 ✅

Root Set에서 도달 불가능
  → 마킹 안됨 (White)
  → 가비지
  → 수집됨 ✅

비유:

  • White: 아직 안 본 책 (마킹 안됨, 수집됨)
  • Gray: 읽는 중인 책 (마킹 중, 살아있음, 수집 안됨)
  • Black: 다 읽은 책 (마킹 완료, 살아있음, 수집 안됨)

예시:

public static void main(String[] args) {
    A a = new A();  // White (마킹 안됨)
    B b = new B();  // White (마킹 안됨)
    C c = new C();  // White (마킹 안됨, 참조 없음)
    a.ref = b;      // A가 B 참조
}

// Root Set 확인:
// 1. Stack의 지역 변수: a (main 메서드)
// 2. Static 변수: A.STR, A.l, A.c 등

// Root Set에서 발견:
a = Gray (Root Set에서 발견, 마킹 시작, 살아있음)
  ↓
a의 자식 확인: a.ref = b
b = Gray (White → Gray, 마킹, 살아있음)
a = Black (마킹 완료, 살아있음 확정)
  ↓
b의 자식 확인: 없음
b = Black (마킹 완료, 살아있음 확정)
  ↓
결과: 
  - a: Black (Root Set에서 도달 가능, 마킹됨, 살아있음, 수집 안됨)
  - b: Black (Root Set에서 도달 가능, 마킹됨, 살아있음, 수집 안됨)
  - c: White (Root Set에서 도달 불가능, 마킹 안됨, 가비지, 수집됨)

⚠️ 최종 정리:

Root Set에서 도달 가능
  → 마킹됨 (Gray 또는 Black)
  → 살아있음
  → 수집 안됨 ✅

Root Set에서 도달 불가능
  → 마킹 안됨 (White)
  → 가비지
  → 수집됨 ✅

비유:

  • Root Set = 책장 정리의 시작점
  • 시작점에서 연결된 책 = 살아있는 책 (마킹됨, 수집 안됨)
  • 연결 안 된 책 = 버릴 책 (마킹 안됨, 수집됨)

⚠️ 핵심 정리:

  • 마킹된 객체 (Gray, Black) = 모두 살아있음, 수집 안됨
  • 마킹 안된 객체 (White) = 가비지, 수집됨
  • 마킹 = 살아있음 보장

🛑 4. STW가 뭔가요? 왜 생기나요?

STW란?

STW(Stop-the-World)는 GC가 실행되는 동안 애플리케이션 스레드를 모두 일시 정지시키는 현상입니다.

쉽게 말하면:

  • GC가 일할 때 애플리케이션이 잠시 멈춤
  • 사용자 요청 처리 중단
  • 모든 스레드가 일시 정지

비유:

  • 도서관 정리 시간에 모든 사람이 나가야 함
  • 정리하는 동안에는 책을 빌리거나 반납할 수 없음
  • 정리 끝나면 다시 이용 가능

실제로는:

애플리케이션 실행 중...
  ↓
GC 시작 (STW 발생)
  ↓
모든 스레드 일시 정지 ⏸️
  ↓
GC 작업 수행
  ↓
GC 완료 (STW 해제)
  ↓
애플리케이션 재개 ▶️

왜 멈춰야 하나요? (왜 STW가 생기나요?)

핵심 이유: GC가 메모리를 안전하게 수집하려면 애플리케이션이 메모리를 변경하면 안 되기 때문입니다!

이유 1: 객체 그래프 일관성 보장

문제 상황 - STW 없이 GC를 하면:

시나리오:
1. GC가 객체 A를 확인 중
   A → B 참조 확인
   "B는 살아있네요"
   
2. 동시에 애플리케이션이 실행 중
   A → B 참조 제거
   C → B 참조 추가
   
3. GC는 A → B만 봤으니
   "B는 가비지네요" (잘못된 판단!)
   
4. 실제로는 C → B로 살아있는데
   B를 수집해버림
   → 프로그램 오류! 💥

해결책: STW

1. 애플리케이션 멈춤 (STW)
2. 객체 그래프가 변경되지 않음
3. GC가 안전하게 확인
4. GC 완료 후 애플리케이션 재개

비유:

  • 사진 찍을 때: 움직이면 흐릿해짐
  • GC도 마찬가지: 메모리가 변경되면 잘못된 판단

이유 2: Root Set 안정성

Root Set은 GC의 시작점입니다:

Root Set (살아있는 객체의 출발점):
  - Stack의 지역 변수
    예: main 메서드의 A a = new A();
  - Static 변수
    예: A.STR = "ABC"
  - JNI 참조

STW 없이 하면:

GC가 Root Set 확인 중:
  Stack: a → A 객체 확인
  
동시에 애플리케이션 실행:
  메서드 종료 → Stack에서 a 제거
  새 메서드 시작 → Stack에 b 추가
  
GC는 혼란:
  "어? a는 없어졌는데?"
  "b는 뭐지?"
  → 잘못된 가비지 판단

해결책: STW

1. 애플리케이션 멈춤
2. Stack이 변경되지 않음
3. Root Set이 안정적
4. GC가 정확하게 판단

비유:

  • 책장 정리 시작점이 계속 바뀌면 정리 불가능
  • Root Set도 마찬가지로 안정적이어야 함

이유 3: 메모리 할당 안전성

GC 중 메모리 할당 시 문제:

GC가 Region A를 수집 중:
  1. Region A의 객체들 확인
  2. 가비지 수집 준비
  
동시에 애플리케이션 실행:
  new C() 호출
  → Region A에 할당 시도
  
결과:
  수집 중인 Region에 할당
  → 메모리 오류! 💥
  → 프로그램 크래시

해결책: STW

1. 애플리케이션 멈춤
2. 메모리 할당 중단
3. GC가 안전하게 수집
4. 수집 완료 후 할당 재개

비유:

  • 집 수리 중에 가구를 옮기면 위험
  • GC도 마찬가지로 수집 중 할당하면 위험

STW가 없으면 어떻게 될까요?

만약 STW가 없다면:

1. GC가 객체 확인 중
2. 애플리케이션이 객체 변경
3. GC가 잘못된 정보로 판단
4. 살아있는 객체를 수집
5. 프로그램 오류 발생 💥

결론: STW는 필수입니다!

  • 안전한 GC를 위해 반드시 필요
  • 다만 시간을 최소화하는 것이 중요

G1GC는 STW를 최소화합니다

STW는 필수지만, 시간을 최소화할 수 있습니다!

G1GC의 STW 최소화 전략:

1. 동시 Marking (Concurrent Marking)

대부분의 작업을 애플리케이션과 동시에 실행:

STW 단계 (짧음):
  Initial Mark: Root Set만 확인 (수 ms)
  
동시 실행 (STW 없음):
  Concurrent Marking: 객체 그래프 탐색
  → 애플리케이션이 계속 실행됨
  
STW 단계 (짧음):
  Remark: 최종 확인 (수 ms)
  Evacuation: 객체 복사 (수십 ms)

비유:

  • 기존 GC: 도서관 전체를 닫고 정리 (오래 걸림)
  • G1GC: 도서관 열어두고 조용히 정리 (빠름)

2. Region 단위 수집

전체 힙을 한 번에 수집하지 않음:

기존 GC:
  전체 힙 수집 (8GB) → STW 수백 ms ~ 수초
  
G1GC:
  Region 단위 수집 (2MB씩) → STW 수십 ms

비유:

  • 기존 GC: 집 전체를 한 번에 청소
  • G1GC: 방별로 조금씩 청소

3. 예측 가능한 STW

목표 시간을 설정할 수 있음:

-XX:MaxGCPauseMillis=200

→ STW 시간을 200ms 이하로 유지하려고 노력
→ 목표 시간 내에 수집 가능한 Region만 선택

하지만 완전히 없앨 수는 없어요:

반드시 STW가 필요한 단계:
1. Initial Mark: Root Set 확인 (STW 필요)
   → 시작점을 안정적으로 잡아야 함
   
2. Remark: 최종 확인 (STW 필요)
   → 동시 Marking 중 변경사항 최종 확인
   
3. Evacuation: 객체 복사 (STW 필요)
   → 객체 이동 중 참조 변경하면 안 됨

STW 시간 비교:

Serial GC:     수백 ms ~ 수초
Parallel GC:   수십 ms ~ 수백 ms
G1GC:          수 ms ~ 수십 ms (목표 설정 가능)
ZGC/Shenandoah: 수 ms 이하 (거의 동시)

결론:

  • STW는 안전한 GC를 위해 필수
  • G1GC는 STW 시간을 최소화
  • 하지만 완전히 제거할 수는 없음
