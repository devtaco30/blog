안녕하세요! 오늘은 개발자 블로그를 만들면서 겪은 문제점과 그 해결책으로 Supabase를 선택한 이유에 대해 이야기해보려고 합니다.

Supabase

이 개발 블로그를 시작한 이유는 이력 소개용이었어요. 그런데 하는 김에, 그동안 개발하면서 또 개발해나가면서 알게 되는 것들을 기록해도 좋을 것 같아서, 포스팅 페이지도 만들게 되었습니다.

처음엔 정적 마크다운 파일로 포스트를 작성하고 Git에 직접 커밋하는 방식을 사용했어요. 방문자가 그렇게 많을 것 같지도 않았고, 저의 사적 공간이 될 거라 생각했었거든요. 그런데 게시물을 4개쯤 써나가니까 이미지를 넣는 방식이나, 게시글을 수정할 때마다 배포를 새로해야 한다거나 하는 불편함이 계속 발생하더라구요.

하지만 그렇다고 해서 백엔드 서버를 별도로 만들고 database instance까지 새로 띄워 진행하는 건 시간과 비용을 모두 낭비하는 거라고 생각됐어요. 방법이 없을까 하고 찾아보니 Supabase를 이용해서 PostgreSQL 엔진과 storage를 사용하면 될 것 같았어요. 그래서 마이그레이션을 진행해보았습니다.

이 글에서는 그 과정과 선택 이유, 그리고 Backend 개발자 관점에서의 장점들을 정리해보려고 합니다.

🚨 기존 정적 블로그의 불편함

1. Firebase vs Supabase 비교

초기엔 저장용 서드파티를 따로 쓸 일이 없을 거라 판단해서 Firebase에 방문자 수 정도만 기록하는 용도로 연동했었어요. 이미 Firebase가 연동되어 있어서, 이걸 이용하면 어떨까 하고도 생각이 들어서 두 서비스를 비교해보았어요.

구분Firebase FirestoreSupabase (PostgreSQL)
🗄️ 데이터베이스NoSQL 문서 기반관계형 데이터베이스
🔍 쿼리 기능제한적 쿼리, JOIN 없음JOIN, 서브쿼리, 윈도우 함수 등 강력한 쿼리
⚡ 트랜잭션제한적 ACID 지원완전한 ACID 트랜잭션
🏗️ 스키마유연하지만 검증 어려움엄격한 스키마, 제약 조건 설정
💰 비용 구조읽기/쓰기 횟수 기반 과금저장 용량 기반 과금
🔒 보안기본 보안 규칙Row Level Security (RLS)
📊 인덱싱자동 인덱싱, 제한적복합 인덱스, 부분 인덱스 등 고급 인덱싱
🔄 실시간실시간 리스너 지원실시간 기능 지원 (현재 미사용)
🌐 API자동 생성, 제한적 커스터마이징REST API + GraphQL, 완전한 커스터마이징

아무래도 게시물과 그 게시물에 들어갈 이미지들을 별도로 적재하고 관리하려면 Supabase가 좀 더 좋을 것 같았고, 비용 구조는 좀 애매했어요. 블로그가 뭔가 폭발적으로 잘 될 거라는 예상은 안되서, 회수 기반 과금이 오히려 나을 것 같았는데, 어차피 Supabase에 프리티어가 있으니 오히려 당장은 프리티어로 충분할 거라 생각이 됐어요. 게시글이 늘어나면 인덱싱도 당연히 필요할테니 PostgreSQL이 좀 더 우위를 점했었습니다.

2. 정적 파일 관리의 한계

  • 에디터 없음: 마크다운 에디터가 없어서 포스트 작성이 불편
  • 관리자 모드 없음: 포스트 관리, 수정, 삭제가 어려움 -> 매번 수정 이후 배포 필요
  • 이미지 파일 관리: 포스트에 들어가는 이미지를 항상 Git에 함께 올려야 함

아마 저처럼 블로그를 간단하게 사용하기 위해 이런 방식으로 운영해보신 분들이라면 이런 불편함을 많이 느끼셨을 거예요. 특히 이미지 하나 추가하려고 해도 Git에 커밋하고 푸시해야 하는 번거로움이 있었죠.

🔍 해결책 탐색 과정

그런데 이런 문제들을 해결하려면 에디터도 만들어야하고, 또 게시글을 작성하면서 들어가는 이미지 관리 (붙여넣기, 드래그앤드랍, 작성 중 삭제 등등) 도 복잡한데다, 그걸 관리할 백엔드 로직, database 를 다 설정해야하는 등 머리가 복잡해져 왔었어요.

백엔드 서버 도입 고려

처음에는 별도의 백엔드 서버를 구축하고 데이터베이스도 별도로 도입하는 것을 고려했어요. "그냥 Spring Boot로 API 서버 하나 만들고, PostgreSQL 연결해서 하면 되겠다" 이런 생각이 들었거든요.

하지만 이는 다음과 같은 문제를 야기했어요:

  • 비용 증가: 서버 호스팅 비용, 데이터베이스 비용
  • 유지보수 복잡성: 서버 관리, 보안 설정, 백업 등
  • 개발 시간 증가: API 설계, 배포 파이프라인 구축 등

위에도 언급했지만, 개인 블로그 하나 운영하려고 서버 비용까지 내는 건 좀 과한 것 같았어요. "이거 뭔가 더 나은 방법이 없을까?" 이런 고민을 하게 되었죠.

Supabase 발견

Cursor AI 에게 상황을 설명하고 괜찮은 플랫폼이 없는지 물어봤죠. Supabase에 를 추천하더군요! 그래서 좀 더 알아보니 꽤 쓸만하다는 생각이 들었어요.

Supabase는 다음과 같은 장점을 제공했어요:

  • PostgreSQL 기반: 강력한 관계형 데이터베이스 기능
  • 백엔드 서버 불필요: 서버리스 아키텍처로 서버 관리 불필요
  • MCP 지원: 개발 편의성 향상
  • 무료 티어: 어느 정도 용량까지 무료로 제공

특히 MCP까지 지원한다는 점이 현재 저에게 정말 매력적이었어요. 만드는 속도가 정말 빨라질 것 같았거든요.

✅ Supabase 선택 이유

솔직히 말하면, 이 정도 기능을 제공하는데 서버 관리할 필요가 없다는 게 정말 놀라웠어요. "이거 진짜 맞나?" 싶을 정도로 좋은 조건이었죠.

1. 기술적 장점

  • PostgreSQL: ACID 트랜잭션, 복잡한 쿼리, 인덱싱 등 강력한 DB 기능
  • Row Level Security (RLS): 데이터 접근 제어 및 보안
  • 실시간 기능: WebSocket 기반 실시간 업데이트
  • 인증 시스템: OAuth, JWT 등 다양한 인증 방식 지원

2. 비용 효율성

  • 무료 티어: 개발 및 소규모 프로젝트에 충분한 용량
  • 서버 비용 없음: 백엔드 서버 구축 및 유지보수 비용 절약
  • 확장성: 필요에 따라 유료 플랜으로 업그레이드 가능

3. 개발 편의성

  • MCP 지원: 개발 도구와의 연동성 향상
  • 자동 API 생성: 데이터베이스 스키마 기반 자동 API 생성
  • 관리 대시보드: 직관적인 데이터베이스 관리 인터페이스

🛠️ 마이그레이션 과정

1. 데이터베이스 설계

Supabase Dashboard에서 posts , visitor_stats 테이블 구조와 RLS 정책 확인
각 테이블의 RLS 정책 상태 (Unrestricted)

게시글과 방문자 통계를 위한 기본적인 테이블 구조를 설계했어요. PostgreSQL의 배열 타입을 활용해서 태그를 효율적으로 관리할 수 있도록 했고, 조회수 추적과 이미지 관리 기능도 포함시켰어요.

2. 환경 설정

GitHub OAuth App 설정
Supabase 에 연동할 Provider 세팅
  • 환경변수 관리: GitHub Secrets를 통한 안전한 설정
  • GitHub Actions: 자동 빌드 및 배포 파이프라인
  • CORS 설정: GitHub Pages와 Supabase 연동

3. 기능 구현

관리자 대시보드에서 게시글 관리 및 이미지 업로드
  • 마크다운 에디터: 포스트 작성 및 편집을 위한 에디터 구현
  • 관리자 모드: 인증된 사용자만 접근 가능한 관리자 페이지
  • GitHub 계정 연동: OAuth를 통한 사용자 인증
  • Supabase 테이블 접근 권한: RLS를 통한 보안 설정
  • 게시글 CRUD: 관리자 페이지를 통한 포스트 관리
  • 이미지 업로드: Supabase Storage를 통한 이미지 관리
  • 방문자 카운팅: 실시간 방문자 통계
  • 조회수 추적: 게시글별 조회수 관리

이제는 정적 블로그에서 느꼈던 모든 불편함들이 해결됐습니다. 관리자인 제 계정으로만 접근 가능한 에디터와 미리보기, 드래그앤드롭으로 붙이는 이미지, 게시글의 CRUD 모두 구현돼서 게시글 관리가 편해졌어요!

🎯 결과 및 개선점

1. 관리 편의성 향상

  • 포스트 작성: 마크다운 에디터를 통한 직관적인 작성
  • 이미지 관리: 드래그 앤 드롭으로 간편한 이미지 업로드

2. 기능 개선

  • 데이터베이스 쿼리: 인덱싱을 통한 빠른 검색
  • 확장성: 향후 기능 추가 시 유연한 확장 가능

3. 비용 절약

  • 서버 비용: 백엔드 서버 구축 비용 절약
  • 유지보수: 서버 관리 시간 및 인력 절약
  • 개발 시간: 기존 인프라 활용으로 개발 시간 단축

📋 결론

정적 블로그에서 동적 블로그로의 전환은 개발하면서 느낀 불편함을 해결하기 위한 개선 작업이었어요. Supabase를 선택한 이유는 강력한 데이터베이스 기능과 백엔드 서버 없이도 구현 가능한 서버리스 아키텍처, 그리고 합리적인 비용 때문이었습니다.

특히 Backend 개발자로서 PostgreSQL의 강력한 기능을 활용할 수 있다는 점이 매력적이었어요. RLS, 트랜잭션, 복잡한 쿼리 등 기존에 별도 서버에서 구현해야 했던 기능들을 Supabase에서 제공하는 API로 간단하게 사용할 수 있다는 점이 큰 장점이었습니다.

🚀 개발자로서 정말 편한 점: MCP 지원

이번 Supabase와의 연동 작업을 할 때 Supabase가 제공하는 MCP와 Cursor AI 연동을 통해 정말 편하게 작업을 했습니다.

Cursor AI 에 Supabse MCP가 연동된 상태
Cursor AI 에 연동된 기능을 통해 테이블 인덱스 상태를 조회

MCP(Multi-modal Context Protocol)가 제공하는 개발 편의성:

  • 데이터베이스 작업 자동화: 복잡한 SQL 쿼리나 DDL 작업을 AI와 함께 구현
  • 실시간 데이터베이스 모니터링: 로그, 성능 어드바이저, 보안 취약점 등 즉시 확인
  • 스키마 설계 및 구현: 테이블 구조 설계, 인덱스 생성, RLS 정책 설정 등을 AI와 함께 진행

실제 경험: 새로운 블로그 시스템을 구축할 때, MCP를 통해 데이터베이스 스키마 설계부터 RLS 정책 설정까지 모든 과정을 AI와 함께 진행할 수 있었어요. 복잡한 보안 정책도 자연어로 설명하고 즉시 구현할 수 있어서 개발 속도가 정말 빨라졌습니다.

결론: MCP 지원은 단순한 기능이 아니라, 개발자의 생산성을 혁신적으로 향상시키는 핵심 요소였어요.

🚀 실무 적용 가이드

Backend 개발자라면:

  • ✅ 정적 블로그에서 동적 블로그로 전환 시 Supabase 고려
  • ✅ PostgreSQL 기반 서버리스 아키텍처 활용
  • ✅ RLS를 통한 보안 설정
  • ✅ GitHub OAuth 연동으로 사용자 인증 구현

블로그 전환 시 체크리스트:

  • ✅ 데이터베이스 설계: 테이블 구조 및 관계 설계
  • ✅ 인증 시스템: OAuth 연동 및 권한 관리
  • ✅ 관리자 기능: 포스트 CRUD 및 이미지 관리
  • ✅ 배포 파이프라인: GitHub Actions 연동
  • ✅ 환경변수 관리: GitHub Secrets 활용

정적 블로그의 한계를 느끼고 있다면, Supabase를 활용한 동적 시스템 전환을 고려해봐도 좋을 것 같습니다.
