안녕하세요. 이번 파트에서는 오더북(Order Book)을 어떻게 구현했는지를 다룹니다.

Phase 1에서 도메인 모델을 검증했으니, 이제 실제 매칭 엔진을 붙일 차례였습니다. 그 시작은 오더북이었습니다.

📋 1. 오더북이란 무엇인가

호가창을 소프트웨어로 표현하면

오더북은 호가창입니다. 현재 시장에 쌓여있는 매수·매도 주문의 목록입니다.

매도 (asks)                매수 (bids)
─────────────────────────────────────
71,000원  500주      70,500원  300주  ← 최우선 매수호가
70,800원  200주      70,000원  150주
70,500원  100주      69,500원  400주

매수 쪽은 높은 가격이 우선입니다. 70,500원을 내겠다는 사람이 70,000원을 내겠다는 사람보다 먼저 체결됩니다. 매도 쪽은 반대로 낮은 가격이 우선입니다.

체결 조건은 단순합니다. 최우선 매수가 ≥ 최우선 매도가이면 체결이 발생합니다. 위 예시에서 최우선 매수 70,500원과 최우선 매도 70,500원이 만났으므로 체결됩니다.

같은 가격에 여러 주문이 쌓여 있다면, 먼저 들어온 주문이 먼저 체결됩니다. 가격-시간 우선 원칙입니다.

어떤 연산이 자주 일어나는가

오더북을 구현하면서 자연스럽게 "어떤 연산이 빈번하게 일어나는가"를 생각하게 됩니다.

  • 매칭이 일어날 때마다 최우선 호가를 조회합니다. 매수 쪽 최고가, 매도 쪽 최저가.
  • 새 주문이 들어오면 같은 가격대의 기존 주문 뒤에 추가합니다. 시간 순서를 유지해야 합니다.
  • 취소 요청이 오면 orderId로 해당 주문을 찾아 제거해야 합니다.

이 세 연산이 효율적이어야 한다는 것을 알게 되면, 그제서야 자료구조 선택의 문제가 됩니다.

연산설명필요 성능
최우선 호가 조회bids 최고가, asks 최저가O(1)
동일 가격 내 FIFO같은 가격이면 시간 순서 유지O(1) 삽입/제거
주문 취소orderId로 바로 찾아 제거O(1)

🤔 2. 어떤 자료구조를 쓸 것인가

가장 먼저 떠오른 것: PriorityQueue

가격 기준으로 정렬이 필요하다는 것을 떠올리면 PriorityQueue가 가장 먼저 생각납니다. Comparator로 가격 정렬을 지정하면 되니까요.

그런데 조금 더 생각해보면 문제가 보입니다.

Comparator에 (가격, 시간) 복합 키를 넣으면 같은 가격 내 시간 순서 자체는 유지할 수 있습니다. 하지만, 문제는 주문 취소입니다.

PriorityQueue는 Java에서 Binary Heap으로 구현돼 있습니다. Heap은 루트가 최솟값(혹은 최댓값)이라는 것만 보장하는 구조입니다. 루트 이외의 원소들은 "부모보다 크다"는 조건만 만족하면 되고, 나머지 위치는 정해지지 않습니다.

그래서 특정 orderId의 주문을 취소하려면 전체를 뒤져야 합니다.

orderId=42를 취소하고 싶다
    → Heap 전체를 O(n) 스캔해서 위치를 찾는다
    → 해당 원소를 제거한다
    → Heap 조건이 깨졌으므로 구조를 재조정한다 — O(log n)
    → 전체 비용: O(n)

O(log n)은 제거 이후 구조를 복구하는 비용입니다. 찾는 것 자체가 O(n)이라 전체는 O(n)이 됩니다. 주문 취소가 잦은 환경에서는 치명적입니다.

LinkedList + Node 직접 참조

O(1) 중간 삭제를 원한다면 LinkedList에 orderId → Node 참조를 직접 들고 있는 방식을 생각할 수 있습니다.

// 취소 시 Node를 직접 꺼내 연결 끊기
Node node = orderIndex.get(orderId);
node.prev.next = node.next;
node.next.prev = node.prev;

삭제 자체는 O(1)이 됩니다. 하지만 다른 문제가 생깁니다.

LinkedList는 노드가 메모리 여기저기에 흩어져 있습니다. 순차 접근할 때마다 캐시 미스가 발생합니다. prev, next 포인터를 직접 다루는 코드는 실수하기 쉽고, 취소 주문이 드문 환경에서는 이 복잡도를 감수할 이유가 없습니다.

Skip List

O(log n) 삽입·삭제·조회를 제공하는 확률적 자료구조로, TreeMap과 비슷한 성능을 냅니다. 다만 Java 표준 라이브러리에 없어 직접 구현해야 하고, TreeMap 대비 체감 성능 차이가 크지 않습니다. 굳이 직접 구현할 이유가 없었습니다.

TreeMap + ArrayDeque 채택

결국 TreeMap과 ArrayDeque를 조합했습니다.

// 매수 호가: 높은 가격 → 낮은 가격 (내림차순)
private final TreeMap<BigDecimal, Deque<OrderEntry>> bids =
    new TreeMap<>(Comparator.reverseOrder());

// 매도 호가: 낮은 가격 → 높은 가격 (오름차순)
private final TreeMap<BigDecimal, Deque<OrderEntry>> asks =
    new TreeMap<>();

// orderId → OrderEntry — O(1) 조회·취소
private final Map<Long, OrderEntry> orderIndex = new HashMap<>();

🏗️ 3. 왜 이 조합인가

TreeMap: 최우선 호가를 O(1)에

TreeMap은 내부가 Red-Black Tree입니다. 삽입·삭제가 O(log n)이고, 항상 정렬된 상태를 유지합니다.

여기서 중요한 건 firstEntry()입니다. 정렬된 트리에서 가장 앞에 있는 원소를 O(log n)이 아닌 O(1)에 가져올 수 있습니다. 매칭마다 최우선 호가를 조회하는 오더북에서 이게 핵심입니다.

bids는 Comparator.reverseOrder()로 높은 가격이 firstEntry()에 오게 하고, asks는 기본 오름차순으로 낮은 가격이 firstEntry()에 옵니다.

ArrayDeque: 같은 가격 내 FIFO

같은 가격의 주문들은 시간 순서를 유지하면서 처리해야 합니다.

// 새 주문 추가: 큐 뒤에 넣습니다
book.computeIfAbsent(entry.getPrice(), k -> new ArrayDeque<>())
    .addLast(entry);

// 매칭 시 앞에서 꺼냅니다
OrderEntry order = queue.peekFirst();

LinkedList 대신 ArrayDeque를 쓴 이유는 메모리 연속성 때문입니다. ArrayDeque는 내부가 배열이라 CPU 캐시를 효율적으로 활용합니다. 노드가 흩어진 LinkedList보다 순차 접근이 빠릅니다.

전체 구조 시각화

bids TreeMap (내림차순)
  70,500 → [주문A(10시01분), 주문B(10시03분)]   ← firstEntry()
  70,000 → [주문C(10시00분)]
  69,500 → [주문D(09시59분)]

asks TreeMap (오름차순)
  70,300 → [주문E(10시02분)]                     ← firstEntry()
  70,800 → [주문F(10시00분)]

매칭 시도:
  최우선 매수: 70,500 (주문A)
  최우선 매도: 70,300 (주문E)
  70,500 ≥ 70,300 → 체결!
  체결가: 70,300 (매도 호가 기준)

⚡ 4. 주문 취소를 어떻게 처리할 것인가

처음 생각: Deque에서 즉시 제거

주문 취소 요청이 오면 해당 주문을 Deque에서 바로 꺼내면 된다고 생각했습니다. 그런데 Deque 중간 삭제는 O(n)입니다. 전체를 순회해야 합니다.

orderIndex에서 OrderEntry를 O(1)로 찾을 수 있어도, 실제로 Deque에서 꺼내는 게 O(n)이라면 소용이 없습니다.

Lazy Removal: 마킹만 하고 나중에 정리

즉시 제거 대신 취소 플래그만 세우는 방식을 택했습니다.

// cancelOrder(): 즉시 제거하지 않고 취소 플래그만 세웁니다
public boolean cancelOrder(Long orderId) {
    OrderEntry entry = orderIndex.remove(orderId);
    if (entry == null) return false;
    entry.cancel(); // 취소 플래그 set — Deque에서는 꺼내지 않습니다
    return true;
}

취소된 엔트리는 Deque에 그대로 남아있지만, orderIndex에서는 제거됩니다. 실제 정리는 match() 호출 시 drainInvalid()가 담당합니다.

// drainInvalid(): 큐 앞에서부터 무효 엔트리를 제거합니다
private void drainInvalid(TreeMap<BigDecimal, Deque<OrderEntry>> book) {
    while (!book.isEmpty()) {
        Deque<OrderEntry> front = book.firstEntry().getValue();
        while (!front.isEmpty()) {
            OrderEntry e = front.peekFirst();
            if (e.isCancelled() || e.getRemainingQuantity() <= 0) {
                front.pollFirst(); // 무효 엔트리 제거
            } else {
                break; // 유효한 주문 발견 → 즉시 종료
            }
        }
        if (front.isEmpty()) {
            book.pollFirstEntry(); // 해당 가격 레벨 제거
        } else {
            break;
        }
    }
}

이게 평균 O(1)인 이유는 간단합니다. 정상적인 상황에서 큐 앞에 취소된 주문이 연속으로 쌓이는 경우는 드뭅니다. 대부분 첫 번째 원소가 유효한 주문이므로 즉시 break됩니다. 취소가 몰리는 극단적인 상황에서도 정리 비용은 취소된 주문 수에만 비례하고, 한 번 정리되면 다시 O(1)로 돌아옵니다.

🔍 5. Kafka 연결하면서 만난 멱등성 문제

같은 주문이 두 번 올 수 있습니다

오더북을 완성하고 Kafka와 연결하면서 새로운 문제가 생겼습니다.

Kafka는 at-least-once 전달을 보장합니다. 컨슈머가 메시지를 처리하다가 장애가 나면, 같은 메시지가 다시 전달될 수 있습니다. 같은 OrderPlacedEvent가 두 번 오면 주문이 오더북에 두 번 들어갑니다.

이를 막으려면 이미 처리한 주문인지 확인할 방법이 필요합니다.

// orderIndex: 현재 오더북에 있는 주문
private final Map<Long, OrderEntry> orderIndex = new HashMap<>();

// filledOrderIds: 전량 체결 완료된 주문 (orderIndex에서 제거된 후에도 추적)
private final Set<Long> filledOrderIds = new HashSet<>();

public boolean containsOrder(Long orderId) {
    return orderIndex.containsKey(orderId) || filledOrderIds.contains(orderId);
}

orderIndex만으로는 부족합니다. 전량 체결된 주문은 orderIndex에서 제거되는데, 이후에 같은 orderId가 다시 오면 중복인지 알 수 없습니다. filledOrderIds에 체결 완료된 orderId를 남겨두어 이 문제를 막습니다.

// 중복 주문 감지
if (book.containsOrder(event.orderId())) {
    log.warn("중복 주문 무시: 종목={} 주문={}", event.stockCode(), event.orderId());
    return;
}

LinkedList + Node 방식이 취소를 O(1)로 처리할 수 있지만, 캐시 효율 저하와 구현 복잡도를 감수해야 합니다. 취소 빈도가 극단적으로 높지 않은 환경에서는 TreeMap + ArrayDeque + Lazy Removal이 균형 잡힌 선택입니다.
